## A 档 · 基础题（6 题）

### A1 [D1-嵌入式C] CRC16 校验是如何实现的？为什么帧尾 CRC 要"低字节在前"传输？

**考察点**：位运算基本功、Modbus 协议字节序习惯。

**参考答案**：
- 实现（src/comm/crc16.c）：`crc` 初始化为 `0xFFFF`；对每个字节 `crc ^= data[i]`，再循环 8 次——最低位为 1 时 `crc >>= 1; crc ^= 0xA001`，否则仅 `crc >>= 1`。多项式 `0xA001` 是 Modbus 标准 0x8005 的逆序反射形式。
- 帧尾字节序（append_crc）：`frame[len] = crc & 0xFF`、`frame[len+1] = crc >> 8`，即 CRC 低字节先发，这是 Modbus RTU 的标准规定。
- 项目用测试向量验证：立三手册示例帧 `01 03 00 04 00 02` → CRC 值 `0xCA85`（帧尾 `85 CA`）；`01 10 00 E8 00 02 04 E0 C0 FF FF` → `0x0DCA`（帧尾 `CA 0D`）。

**追问方向**：多项式为什么要用反射形式？查表法与逐位法的取舍？CRC 能防住哪些错误、不能防哪些？

**追问参考**：
- 反射形式原因：Modbus RTU 规定 LSB-first 逐字节处理且 CRC 低字节先发，0x8005（x16+x15+x2+1）的位序被反射成 0xA001，与移位方向（右移）配套，实现最简单：每字节 8 次右移 + 条件异或，无需处理位反转。若坚持用 0x8005 需额外做位反转，代码复杂度高且易错。
- 查表 vs 逐位：逐位法省内存（几十字节）、代码直观、每字节 8 次循环；查表法用 256 项 16 位表（512 字节）换速度（每字节 1 次查表 + 异或），适合高波特率/高频收发。本项目波特率 115200、帧长 <20 字节，逐位法性能足够，保持纯 C 可移植。
- CRC 防错能力：CRC16 可检出全部 1 位错、2 位错、奇数位错，以及长度 ≤16 位的突发错误；不能保证检出任意长度的突发错误（概率性漏检 ~1/65536），也不能对抗"对端故意构造的合法帧"。因此 CRC 校验通过 ≠ 数据语义正确（如字节序错误、寄存器地址错位时 CRC 依然能过，这也是 C6 题强调协议审计的原因）。

### A2 [D2-Modbus] Modbus RTU 帧由哪几部分组成？项目用到了哪些功能码？

**考察点**：Modbus 协议基础、帧格式认知。

**参考答案**：
- 帧格式：`[从站地址][功能码][数据...][CRC低][CRC高]`。
- 项目功能码（src/comm/modbus_rtu.h）：
  - `03H` 读保持寄存器：读位置 0x0004~0x0005、状态 0x0006~0x0007（连续 2 个寄存器拼 32 位）；
  - `04H` 读单寄存器：立三 V126 手册扩展，读实时电流 0x001A（帧格式与 03H 相同）；
  - `06H` 写单寄存器：使能 0x00D4、启停 0x00C8、关限位 0x006D 等 16 位命令；
  - `10H` 写多寄存器：写 32 位速度 0x00D8~0x00D9、绝对位置 0x00E8~0x00E9。
- 异常响应：功能码置 `0x80` 位（如 `0x83`），帧长 5 字节，第 3 字节为异常码，`modbus_parse_response` 返回 `ERR_EXCEPTION`。

**追问方向**：06H 与 10H 响应帧的差异？地址域 0 和 1~64 的含义？广播地址为什么不回应？

**追问参考**：
- 06H 与 10H 响应差异：06H 响应 = 请求帧**原样回显**（8 字节，含写入值），主站可校验写入是否正确；10H 响应只回"从站地址 + 功能码 + 起始地址 + 寄存器数量"（8 字节），**不回数据区**。`modbus_parse_response` 按功能码分派：06H 可提取回显值，10H 只确认地址/数量。
- 地址域含义：0 = 广播地址，所有从站执行但不回复；1~64 = 子节点地址，本项目约定从站地址依次 1~6。
- 广播不回复的原因：广播是"一对多"指令，若所有从站同时回复会造成总线冲突（多帧叠加、CRC 必失败）；且主站无法把多帧回复对应到具体从站。因此广播只用于无需确认的写操作（如统一启停、统一设参数）。

### A3 [D3-运动学] 什么是 DH 参数？本项目 DH 表中的 theta_offset 起什么作用？

**考察点**：DH 建模基本概念、零位约定。

**参考答案**：
- 标准 DH 四参数（config/dh_params.h）：
  - `a`：连杆长度（沿 x_i 方向，从 z_{i-1} 到 z_i）；
  - `alpha`：连杆扭转（绕 x_i 轴，从 z_{i-1} 转到 z_i）；
  - `d`：连杆偏距（沿 z_{i-1} 方向，从 x_{i-1} 到 x_i）；
  - `theta_offset`：关节零位偏移（rad）。
- theta_offset 的作用：把机械臂的机械 home 姿态编码进 DH 表。J2 的 home=-90°、J3 的 home=90° 写入 offset，`dh_forward` 中 `theta = q×π/180 + theta_offset`，使 **q=0 时 FK 输出机械 home 姿态**，电机零位与模型零位一致。
- 真实参数示例：J1 {a=35, d=140, alpha=-90°}（D_BS=35/L_BS=140）、J2 {a=146, alpha=0°}（L_AM=146）、J6 {d=183}（L_WT=183）。

**追问方向**：为什么 J2/J3 的 home 角度必须写进 offset 而不是另存？标准 DH 与改进 DH 的区别？

**追问参考**：
- 必须写进 offset 的原因：DH 正解公式中 theta 是唯一的关节变量，若把 home 角另存，每次 FK 都要额外加偏移，容易在 IK 反解、限位判断、单测多处遗漏导致零位不一致；写入 DH 表后 q=0 直接对应机械 home 姿态，IK 输出的 q 也天然是相对零位的角度，正逆解、轨迹规划、限位筛选全链路零位约定一致。
- 标准 DH vs 改进 DH：标准 DH（经典 Denavit-Hartenberg）变换顺序为 Rotz·Transz·Transx·Rotx，参数挂在相邻坐标系上；改进 DH（Craig）为 Rotx·Transx·Rotz·Transz，参数挂在自身坐标系。同一机械臂两套参数数值不同（a/alpha 位置定义不同），混用会导致 FK 错误；项目采用标准 DH（dh.c 中 4x4 齐次矩阵逐项构造），整套参数与算法必须配套使用。

### A4 [D4-轨迹规划] 梯形速度规划分哪几段？为什么短距离会退化为三角轮廓？

**考察点**：轨迹规划基础模型。

**参考答案**：
- 梯形规划三段（src/trajectory/planner.c `trap_plan`）：T1 匀加速、T2 匀速、T3 匀减速（对称，T3=T1），初末速度均为 0。
- 参数计算：加速段位移 `s_acc = vmax²/(2·amax)`；若 `2·s_acc ≥ |dist|`，说明距离不足以跑到 vmax 再减速，此时退化为**三角轮廓**：峰值速度降为 `vp = √(|dist|·amax)`，匀速段 T2=0。
- 求值 `trap_eval`：按三段积分位置、速度、加速度；t 超出总时长时按终点返回。

**追问方向**：为什么要做"距离不足"判断？如果直接按 vmax 规划会怎样（到位前速度减不到 0）？反向运动如何处理（dir 符号）？

**追问参考**：
- 距离不足判断的意义：梯形规划必须满足"加速到 vpeak 的距离 + 从 vpeak 减速到 0 的距离 ≤ 总行程"，否则在行程中点速度还降不下来，会出现越过目标再反向、末端速度不为 0 的振荡；先按"是否能到 vmax"分派三角/梯形轮廓，是规划器正确性的前提。
- 直接按 vmax 规划的后果：若 `2·s_acc > dist` 仍用 vmax，轨迹在到达终点时速度仍 >0（减不到 0），机械上表现为"冲过头/撞击"；若把减速段强行塞进剩余距离，加速度会超过 amax，违背规划约束。因此必须降峰值速度 vp=√(|dist|·amax)。
- 反向运动处理：规划前取 `dir = sign(dist)`（如 q1<q0 时 dir=-1），所有位移计算用 |dist|，求值时位置按 `q0 + dir·s(t)`、速度/加速度按 `dir·v(t)` 输出；这样一段规划代码同时覆盖正反向，测试用例"梯形-反向 30→-40"即验证该路径。

### A5 [D5-架构] 项目的三层分离架构是怎样的？为什么这样分层？

**考察点**：嵌入式软件分层思想、依赖方向。

**参考答案**：
- 三层（CMakeLists.txt 静态库分层 + 依赖关系）：
  - comm：Windows 串口封装（serial_win.c）、CRC16、Modbus RTU 帧构造/解析（modbus_rtu.c），对外暴露 CommOps 接口；
  - control：关节使能/运动/状态读取（robot.c）、堵转回零（home.c）、在线监控（monitor.c），**只依赖 comm_if.h 抽象接口**，不直接依赖具体串口实现；
  - main.c：CLI 命令循环（cmd_parser），组合 control 与 tools。
- 另有 kinematics（正逆解）、trajectory（插补）、config（参数）、utils（错误码/日志/命令解析）。
- 分层收益：依赖单向（control→comm 接口、main→control）、串口实现可整体替换、各层可独立离线单测（comm 可注入内存假串口、kinematics/trajectory 纯数学无硬件依赖）、回单片机时只需替换 comm 层。

**追问方向**：control 层为什么不直接 include modbus_rtu.h（前向声明 ModbusFrame）？如果新增一种总线（如 CAN）需要改哪些文件？

**追问参考**：
- 不 include modbus_rtu.h 的原因：control 层只需"帧对象"传递，不需要知道帧如何构造/解析（那是 comm 层的职责）；robot_internal.h 用 `typedef struct ModbusFrame ModbusFrame;` 前向声明打破编译期强依赖，comm 内部实现变更（改字段、改缓冲策略）不触发 control 层重编译；移植到单片机换串口实现时 control 也无需改动。
- 新增 CAN 总线：只需新增一个实现 CommOps 的 can_comm.c（把 CAN 收发映射成 read_frame/write_frame 语义），再 `modbus_comm_set(&can_comm_ops)` 注入即可；若 CAN 上的应用协议不是 Modbus RTU，则替换 modbus_rtu.c 的帧编解码（对外仍暴露 transact 语义），上层 control 接口完全不变——这正是三层分离的收益。

### A6 [D6-调试排障] 立三电机没有堵转寄存器，项目如何判断碰撞/堵转？

**考察点**：硬件能力约束下的方案设计思维。

**参考答案**：
- 立三（LEESN）无堵转电流/堵转逻辑专用寄存器，碰撞/堵转判定**唯一依据是 PC 侧轮询 0x001A 实时电流（mA）**。
- 回零场景（src/control/home.c）：速度模式顶硬限位 → 每 200ms 轮询电流，当 `电流 > 堵转阈值 + HOME_STALL_MARGIN_MA(400)` 判定堵转 → 急停（0x00C8=0x0100）→ 清零位置（0x00D2~0x00D3=0）→ 标记到位。
- 监控场景（src/control/monitor.c `monitor_check_stall`）：电流超阈值即报警，阈值来自配置（stall_current_ma_1..6，默认 3000mA，可差异化标定）。
- 保护细节：电流读数 >3000mA 视为通信异常值，忽略本次判定，避免误报。

**追问方向**：电流阈值如何标定？误报/漏报如何权衡（余量设计）？如果电流读不到（通信失败）该怎么处理？

**追问参考**：
- 阈值标定：空载与额定负载下实测各轴正常运动电流，取"正常运行电流上限 × 安全系数（1.5~2 倍）+ 余量"作初值；再人为堵转/碰撞测实际堵转电流，确认阈值高于正常值、低于堵转值；六轴因负载/减速比不同（2 号 100:1）应分开标定，写入 stall_current_ma_1..6，回零时再加 HOME_STALL_MARGIN_MA(400) 余量。
- 误报/漏报权衡：阈值过低 → 加速/爬坡等正常大电流场景误报急停；过高 → 漏报导致顶坏机械。折中方案是加"持续超阈值时间"判据（连续 N 次采样超阈值才报警），滤掉瞬时电流尖峰，同时阈值不必刻意压低。
- 电流读不到：robot_read_current_ma 失败返回 -1，监控逻辑应区分"读失败"与"电流超限"——把读失败记为通信错误计数而非堵转，连续失败按离线处理（报警/停轴），避免把通信故障误判成碰撞造成误急停。

## B 档 · 进阶题（6 题）

### B1 [D1-嵌入式C] 讲解项目的 DWORD 字节序契约："低 16 位寄存器在前、字内高字节在前"。

**考察点**：32 位数据在 Modbus 帧中的排列、组合拆分的位运算。

**参考答案**：
- 契约（robot_internal.h 中写明，经立三手册全部示例帧自洽验证）：立三 32 位寄存器（INT32/UINT32）在帧中 **低 16 位寄存器在前、字内高字节在前**。
- 写（10H）：`values[0]=低16位、values[1]=高16位`，构造器按数组序逐字大端发送（put_u16_be）。示例：写 -8000 脉冲 → `values={0xE0C0, 0xFFFF}` → 帧数据 `E0 C0 FF FF`（手册 p21 CRC=0x0DCA）。
- 读（03H）：响应 `data[0..1]=低16位、data[2..3]=高16位`。组装代码（robot.c `robot_read_position_steps`）：`(int32_t)(((uint32_t)data[2]<<24) | ((uint32_t)data[3]<<16) | ((uint32_t)data[0]<<8) | data[1])`。
- 单测覆盖（tests/test_modbus.c）：预置响应 `E0 C0 FF FF` 解析出 -8000，防止字节序回归。
- 注意字内仍是大端（`get_u16_be/put_u16_be` 逐字不变），只是寄存器排列顺序特殊。

**追问方向**：若按"高字在前"解析，-8000 会被读成多少？为什么不能直接 memcpy 成 int32？跨平台时大小端又有什么坑？

**追问参考**：
- 按高字在前解析的数值：帧字节 `E0 C0 FF FF` 若按"高 16 位寄存器在前"组合，得到 0xE0C0FFFF ≈ 37.7 亿（按 int32 为 -506458009），与 -8000 完全不符——位置命令会变成天文数字，电机飞车或拒绝执行，这正说明字节序契约必须严格遵守。
- 不能直接 memcpy：x86 小端主机内存中 int32 -8000 的字节序是 `C0 E0 FF FF`（低字节在低地址），与帧要求 `E0 C0 FF FF` 不同；直接 memcpy 会按主机字节序发出，语义错误。正解是显式按协议拼字节（put_u16_be 逐字大端 + 寄存器低字在前），协议与主机字节序解耦。
- 跨平台坑：大端主机上若偷懒用"主机字节序"发送同样出错；统一用 get_u16_be/put_u16_be 显式组装后，任意主机字节序下帧内容一致。另一个坑是负值右移的符号扩展——组装 32 位时须先把负值提升为 uint32_t 再移位，否则高位补 1 造成拼接错误。

### B2 [D2-Modbus] modbus_transact 的完整时序是什么？RS485 半双工噪声过滤为什么只能加在电机回程方向？

**考察点**：总线事务时序设计、半双工物理特性。

**参考答案**：
- 时序（src/comm/modbus_rtu.c `modbus_transact`）：`flush → write_frame(tx) → read_frame(rx, 200ms超时) → modbus_parse_response`。
  - 先 flush：PurgeComm 清空收发缓冲，防止上一次残留脏数据误入本帧解析；
  - 写请求帧完整发出；
  - 读响应（200ms 超时，超时返回 ERR_TIMEOUT）；
  - 解析：CRC 校验 + 帧长/功能码校验（异常响应、03H/04H/06H/10H 分派）。
- 半双工噪声过滤位置（项目实测教训）：RS485 同一对线半双工，PC 发送时会产生自收/回显噪声。**噪声过滤只能加在电机回程方向（PC 接收）**；PC→RS485 发送方向不得过滤 bit7=1 的字节——因为 Modbus CRC 低字节常为 0x85/0xFC 这类高位置 1 字节，误过滤会截断 CRC，电机收到不完整帧导致无响应。
- 实现中把过滤逻辑放在接收侧解析前，发送路径原样直出。

**追问方向**：除了过滤，还有哪些手段抑制半双工噪声（方向切换延时、收发使能控制、flush）？为什么 200ms 超时足够（波特率 115200 下 8 字节帧约 0.7ms）？

**追问参考**：
- 其他抑制手段：①方向切换延时——写完后延时（1~2ms）再切到接收/读，让 RS485 收发使能稳定、自收回显结束；②收发使能控制——用 DE/RE 引脚控制方向，写期间禁止接收或屏蔽自身回显；③flush——事务开始前 PurgeComm 清收发缓冲，防残留脏数据混入；④总线电平——加终端电阻（120Ω）与偏置电阻消除反射/不定态；⑤帧间隔——遵守 RTU 3.5 字符静默，防帧粘连。
- 200ms 超时合理性：115200bps 下 1 字节 ≈ 86.8μs，8 字节响应 ≈ 0.7ms；200ms 是响应时间的 200 倍以上，足以覆盖从站固件处理时间（通常 <10ms）与总线偶发重试。设大超时是为了"单轴失败不卡死整组"——回零 200ms 轮询周期即按此超时设计，配合 HOME_STUCK_MS 重发机制保证状态机可收敛。

### B3 [D3-运动学] 球腕解耦解析 IK 为什么最多 8 组解？如何筛选最优解？

**考察点**：解析逆解数学结构、多解管理。

**参考答案**：
- 8 组解来源（src/kinematics/ik.c，肩×2、肘×2、腕×2）：
  - **肩部 2 解**：腕心水平距离 `U = ±√(r²-d3²)`，对应肩部翻转；
  - **肘部 2 解**：`s3 = (P²+Y²-a2²-d4²)/(2·a2·d4)`，`c3 = ±√(1-s3²)`；
  - **腕部 2 解**：`sinθ5 = ±√(1-r33²)`（θ5 取 (0,π) 或 (-π,0)），θ4/θ6 由 atan2 反解。
- 关节角输出：`q = norm_angle(theta - theta_offset)` 归一到 (-π,π] 再转度。
- 筛选两级（ik.h 接口）：
  1. `ik_filter_by_limits`：按各关节软限位 `[min_deg, max_deg]` 过滤；
  2. `ik_select_best`：对剩余候选按**加权关节距离** `Σ w_i·(θ_i - θ_current)²` 最小取最优（weights 为 NULL 时全 1），保证运动连续、避免解跳变。
- 单测（tests/test_fk_ik.c）验证每组解 FK 闭环误差 < 1e-6。

**追问方向**：为什么球腕（后三轴交于一点、a4=a5=a6=0）是解析解的前提？如果第 3 轴不交会怎样？加权选最优时权重如何设计？

**追问参考**：
- 球腕前提：解析 IK 用"腕心分离"——先把末端姿态问题退化为"腕心位置（前 3 轴）"与"腕部姿态（后 3 轴）"两个子问题。只有当 J4/J5/J6 轴线交于腕心（本项目 alpha4=-90°、alpha5=+90°、a4=a5=a6=0）时，腕心位置才与腕部角度无关，前 3 轴可独立解出；后 3 轴由剩余姿态矩阵 atan2 反解。这是工业六轴最常见的构型。
- 若不满足球腕（a4/a5/a6 非零）：腕心位置耦合腕部角度，无法分离成两个 3 自由度子问题，解析闭式解不再存在，只能走数值迭代（牛顿/雅可比阻尼最小二乘）求 IK——收敛性、初值、奇异性处理都复杂得多。
- 权重设计：`ik_select_best` 的权重向量 w_i 决定"优先少动哪根轴"。通常大关节（J1/J2 惯量大、减速比 50~100:1）给较大权重、腕部小关节给小权重，使选解更符合"少动大臂"的运动习惯；特殊场景（如保持工具姿态）可对特定轴加大权重；weights 传 NULL 时全 1（等权）。权重不当会导致选解在大臂位置附近频繁换解（抖动）。

### B4 [D4-轨迹规划] S 曲线 7 段结构是什么？如何求实际峰值速度？为什么 S 曲线总时长不小于梯形？

**考察点**：jerk 受限规划原理、数值方法。

**参考答案**：
- 7 段（src/trajectory/planner.c `s_plan`，对称）：T1 加加速（acc 线性增）→ T2 恒加速 → T3 减加速 → T4 匀速 → T5 加减速 → T6 恒减速 → T7 减减速。加速度连续、无冲击，jerk 受限。
- 分段参数：`T1 = amax/jmax`，`T2 = vpeak/amax - T1`；若 `T2 < 0`（距离过短达不到 amax），退化为 `T1 = √(vpeak/jmax), T2 = 0`。
- 求实际峰值速度：`2·s_acc_displacement(vpeak) ≤ |dist|` 的最大 vpeak（≤vmax），用 **64 次二分**逼近，避免无解或超限。
- 与梯形对比：同一组 vmax/amax 下，S 曲线因加加速段的存在，加速到 vpeak 需更多时间，`t_total` 不小于梯形（tests/test_planner.c 显式断言）。
- 边界：零位移/非法参数退化走梯形；求值按 7 段分别积分位置/速度/加速度。

**追问方向**：jmax 为 0 时为什么退化到梯形？二分法终止条件（64 次）精度够吗？如果直接令 vpeak=vmax 会怎样（匀速段为负）？

**追问参考**：
- jmax=0 退化原因：S 曲线公式中 `T1 = amax/jmax`，jmax=0 时 T1→∞ 无意义；物理上 jmax=0 表示"加加速度无穷大"，即加速度可阶跃变化，正是梯形轮廓（梯形允许加速度瞬时跳变）。代码中 jmax<=0 直接走 trap_plan。
- 64 次二分精度：区间初始为 [0, vmax]，每次折半，64 次后宽度为 vmax/2^64，远超 double 尾数精度，可视为收敛到浮点最优；实际 20~30 次已足够，64 是"安全上限"风格，不牺牲可读性。
- 直接 vpeak=vmax 的后果：当距离不足时 2·s_acc > |dist|，匀速段 T4（或恒加速段 T2）算出负值 → 时间轴倒退，planner_eval 在部分 t 上位置/速度不单调甚至反向，违反"位置单调、限幅"的单测断言，机械上表现为抖动/过冲。

### B5 [D5-架构] CommOps 是什么？如何实现"离线可单测（不接硬件）"？

**考察点**：依赖注入/接口抽象在纯 C 中的落地、可测试性设计。

**参考答案**：
- CommOps（src/comm/comm_if.h）是纯 C **函数指针表**：`{open, close, read_frame, write_frame, flush}`，control 层唯一可见的 comm 头文件。
- 注入方式：全局指针 `g_comm_ops`，由 `modbus_comm_set(&serial_comm_ops)` 注入真串口实现；未注入时 `modbus_transact` 返回 `ERR_PORT`。
- 离线单测（tests/test_modbus.c）：构造 `g_fake_comm_ops` 内存假串口——`fake_write_frame` 记录主站写出的请求帧并"上线"预置应答，`fake_read_frame` 逐字节吐出，完整模拟一次主从往返，验证帧收发一致、CRC、异常响应、未注入返回 ERR_PORT。
- 配置双轨（方案二）：编译期固定参数（CRC 多项式、功能码、DEG2STEPS 系数、8N1）只走宏；运行时可变参数（串口、从站地址、电流阈值、软限位）走 robot_config.ini，宏仅作默认值兜底；main 启动打印"生效来源：ini/默认"。

**追问方向**：函数指针表与 C++ 虚函数/接口的异同？为什么 read_frame 无句柄参数（实现方自持全局状态）？如果两个串口实例并存怎么办？

**追问参考**：
- 函数指针表 vs C++ 虚函数：两者都是"接口-实现"分离的运行时多态；C++ 虚函数由编译器维护 vtable、支持继承与重写，但引入运行时类型信息与对象模型；纯 C 函数指针表更轻量、可见、可控（一张 struct 填函数指针即可），只需 C11 编译、无 C++ 运行时依赖，契合"纯 C 可移植回单片机"的约束；缺点是没有继承、需手动保证实现签名一致。
- read_frame 无句柄参数：CommOps 采用"实现方自持全局状态"——serial_win.c 内部 static 保存 HANDLE，open 时写入、read/write 时读取，接口因此极简稳定；代价是单例限制（同一时刻只能一个串口），与项目"PC 直驱一条 RS485 总线"的形态匹配。
- 两个串口并存：①CommOps 增加 `void *ctx` 参数（open 返回句柄、后续传入），接口与所有实现/调用点都要改，最干净但属架构变更需先评审；②"实例表"方案（CommOps + 私有状态数组按索引取）保持签名不变；③复制一套模块（不优雅）。当前单总线约束下维持现状即可。

### B6 [D6-调试排障] 堵转回零的完整流程与状态机是什么？为什么 6 号关节堵转阈值配 0？

**考察点**：复杂流程设计、异常状态机、参数语义。

**参考答案**：
- 流程（src/control/home.c `robot_home`）：
  1. **分组**：组0 `{1,2,3,5,6}` 并行堵转回零 → 组1 `{4}` 单独回零（4 号后处理避免机械干涉/电流不均）；
  2. **arm 电机**（`home_arm_motor`）：0x00D4 写 0 使能 → 0x006D 关限位（纯靠电流判碰撞，避免限位开关提前截停）→ 0x00D8~0x00D9 写运行速度 → 0x00C8 写 1/257 启动，台间 Sleep(10ms) 防帧粘连；
  3. **轮询堵转**（`home_grp_stall_scan`，200ms 间隔）：读状态/电流/位置；`电流 > 阈值+400mA` → 急停 0x00C8=0x0100 → 清零 0x00D2~0x00D3=0 → 标记到位；若状态非"正在运行"且超过 `HOME_MIN_RUN_MS(2000)`，累计 `HOME_STUCK_MS(1500)` 未恢复则**重新下发运行命令**（防丢帧导致电机停住）；
  4. **运动到机械原点**：全部堵转到位后，movej 到 `HOME_POSE_DEG`，`wait_group_idle` 等非运行态；
  5. **恢复**：使能 + 0x006D 开限位。
- 6 号关节 `HOME_STALL_CURRENT_MA=0`：表示该轴**无堵转场景**（无硬限位可顶），不参与电流堵转判定，靠运行状态/超时机制收敛，避免误判。

**追问方向**：为什么回零要"关限位"？急停用 0x0100 而不是 0x0000（减速停）的差异？分组并行与串行的取舍？

**追问参考**：
- 关限位原因：回零的目的是"撞出机械原点"，若保留软/硬限位（0x006D=1），运动到限位处会被驱动器提前截停或报警，无法到达真正的机械原点，也无法用电流上升作为到位判据。项目在 home_arm_motor 中显式写 0x006D=0（关闭限位），靠 0x001A 电流超阈值判定"顶死"；回零完成后恢复 0x006D=1。
- 0x0100 与 0x0000 差异：0x00C8 写 0x0000 = 减速停（驱动器按减速时间平滑停下），写 0x0100 = 急停（立即切断力矩）。堵转瞬间若用减速停，驱动器还会继续顶着限位走一段，位置清零的基准不一致；急停立即停住，保证"堵转位置 = 机械原点"的复位精度，也避免长时间堵转过热。
- 分组并行 vs 串行：并行（组0 {1,2,3,5,6}）缩短整机回零时间（6 轴共 2 组 vs 串行 6 组）；但并行时多轴同时顶限位，总线轮询压力大（每 200ms 轮询 5 轴），且机械上可能因多轴联动产生额外干涉。项目把 4 号单独放组1，是因为 4 号运动会影响整臂姿态，与其余轴同时顶限位可能卡死/过流——先复位大臂再单独复位小臂轴，兼顾时间与安全。

### C1 [D1-嵌入式C/综合排障] 现场出现"偶发收帧 CRC 校验失败"，你会如何定位根因？

**考察点**：现场排障方法论、协议时序与物理层认知。

**参考答案**：
- 第一步：抓包确认"失败帧"长什么样——是帧被截断（长度不足）、字节错位，还是内容被污染；对比正常帧与失败帧（记录 hex）。
- 第二步：检查噪声过滤位置（本项目已验证的坑）——过滤只能加在 PC 接收（电机回程）方向；若误加到发送方向，bit7=1 的 CRC 低字节（如 0x85/0xFC）被滤掉，电机收到残缺帧 → 超时或对端无响应。
- 第三步：检查 Modbus RTU 帧间隔——RTU 要求帧间 ≥3.5 字符静默时间；连续轮询（如回零多轴）若帧粘连，从站会把两帧当一帧，CRC 必失败；本项目组间 Sleep(10ms) 即为此。
- 第四步：检查 RS485 方向切换——半双工收发自激、A/B 线接反、终端电阻缺失导致反射，都会造成偶发坏帧；flush 后立即写可能收到自身回显。
- 第五步：确认波特率/校验一致（115200 8N1）、线缆长度与屏蔽。
- 第六步：回归 CRC 实现——用手册示例向量验证（test_crc16：0xCA85/0x0DCA），排除算法本身问题。

**追问方向**：偶发（概率性）与持续（确定性）故障的排查策略差异？如何用单测复现"坏帧注入"场景？

**追问参考**：
- 策略差异：持续故障多为确定性原因（参数配置错、接线错、协议实现错），按"最小复现→二分定位"快速收敛；偶发故障多为时序/干扰/边界（帧粘连、方向切换、电磁干扰、超时边界），需先做统计（抓包记录失败帧的时间分布、内容模式），再围绕差异点设计对照实验（降低波特率是否消失、加延时是否消失、换线/加终端是否消失），用"改变单一变量"逼近根因。
- 坏帧注入单测：利用 CommOps 假串口可离线构造——①注入错误 CRC 的应答（test_modbus 已有"坏 CRC 拒绝"用例）；②注入长度错误/功能码异常/地址不符的帧，断言返回 ERR_LEN/ERR_EXCEPTION；③模拟截断（应答只发一半，read_frame 返回短帧）与超时（应答为空），断言 ERR_TIMEOUT；④模拟字节错位/粘连（两帧拼一次吐出），验证解析器按帧边界正确丢弃或报错；⑤可加"随机坏帧比例"参数，跑模糊式回归（如每 100 帧注入 1 帧坏帧，统计业务层不误动作）。这类用例不依赖硬件，适合 CI 常驻。

### C2 [D2-Modbus/多机联调] 6 台电机如何设置从站地址？若出现多台同地址，总线会发生什么？如何排查？

**考察点**：多从站组网、现场实施细节。

**参考答案**：
- 配置流程（立三手册）：每台驱动器基地址寄存器 0x0066 默认 1，多台需**逐台设置**——每次只让一台在线（其余断电或隔离），写 0x0066=目标地址，再写 0x00DC=1 断电保存；0x0067 为地址源。项目约定从站地址依次 1~6。
- 扫描工具（src/tools/scan_motors.c）：遍历从站地址（默认 1..16），发 03H 读 0x0066，有有效响应即判定在线并打印设备地址。
- 同地址后果：主站发帧后**多台从站同时回应**，总线上多帧叠加 → 接收端 CRC 失败/超时/解析错乱，表现为"某关节时好时坏"。
- 排查：跑 scan_motors 列出在线地址与读到的 0x0066 值，找出重复地址；逐台断电重新设置并断电保存；确认接线星型/菊花链拓扑与终端匹配。

**追问方向**：广播地址（0）有什么用？如果某台地址设为 0 会怎样？修改地址时断电保存失败（0x00DC 写 1）会有什么后果？

**追问参考**：
- 广播地址（0）用途：Modbus 地址域 0 表示广播，所有从站同时接收并执行，但**不回应**，适用于"同时启停/同时使能/统一写参数"类操作，节省总线时间。本项目按立三手册将地址域限定为 1~64 子节点，未使用广播，原因是 6 台电机需要分别确认到位/状态，单播回执更有价值。
- 地址设为 0 的后果：若某台驱动器 0x0066 被误设为 0，它会把所有目标为本机地址的指令当广播接收（不回执），主站永远等不到它的响应 → 该轴表现为"收不到位置/电流、movej 超时"，且同一帧可能被多台响应造成总线冲突；这也是 scan_motors 扫到"地址 0 在线但响应异常"时的排查点。
- 断电保存失败后果：0x0066 写入的是 RAM 内运行地址，0x00DC=1 才写入非易失存储；若只改 0x0066 未写 0x00DC 或写入失败（如总线断电），**重启后地址回退为出厂值 1**，导致多台都变 1 → 总线冲突。工程上要求"逐台改地址 + 写 0x00DC + 断电重启 + scan_motors 复核"四步闭环，防止地址回退。

### C3 [D3-运动学/奇异处理] IK 中遇到奇异位形时项目如何处理？为什么 s3 越界不 clamp 成伪解？

**考察点**：数值鲁棒性、算法诚实性。

**参考答案**：
- 三类奇异处理（src/kinematics/ik.c）：
  1. **肩奇异**：`r ≤ |d3|`（腕心水平距离不足以容纳 d3 偏距），`ik_solve` 直接返回 0；
  2. **腕奇异**：`|sinθ5| < IK_EPS(1e-10)`，θ4 与 θ6 同轴、r13/r23 同时为 0，atan2 无定义 → 该组 `ok=0` 跳过；
  3. **肘不可达**：`s3` 超出 [-1,1]（腕心超出肘部可达半径）→ `continue` 跳过该肩部姿态。
- 不 clamp 的原因：把 s3 夹到 ±1 会生成**不满足目标位姿的伪解**——解出来 θ2/θ3 组合的 FK 结果与目标位姿不符（FK→IK→FK 闭环误差超标），工程上"给一个能动的错解"比"明确无解"更危险。
- 质量保障：tests/test_fk_ik.c 对 5 组典型/非奇异位形做 FK→IK→每组解再 FK 闭环，位姿误差 < 1e-6；注释明确"全零位形为肘伸直+腕奇异，IK 数学上无解"，测试用例刻意避开。

**追问方向**：奇异附近（sinθ5 很小但不为 0）数值上会怎样（放大噪声）？工程上如何在奇异附近做平滑过渡（阻尼最小二乘/奇异分离）？

**追问参考**：
- 奇异附近数值特性：θ5→0 时 r13、r23 同时趋 0，`atan2(-r13, r23)` 的分子分母都接近 0，微小位姿误差/浮点噪声会显著改变 θ4/θ6 的比值（信噪比恶化），θ4 与 θ6 变成"大小相反的两个大角"（旋转方向相反互相抵消），关节速度被急剧放大——末端轻微抖动，腕部两轴高速对转，机械上冲击大。
- 平滑过渡手段：①**奇异区域减速/规避**——事先计算奇异度量（如 |sinθ5| 或雅可比条件数），接近阈值时限制规划速度/加速度；②**阻尼最小二乘（DLS）**——对雅可比求逆时加阻尼项 λI（λ 随奇异度自适应），在精度与关节速度间折中，避免病态求逆放大；③**奇异分离法**——把雅可比分成可解与不可解子空间，只在奇异子空间内做阻尼处理，保留非奇异方向的精度；④**奇异等价处理**——对腕奇异固定 θ4 与 θ6 的比值/约束其一，牺牲一点姿态精度换运动连续；⑤解析 IK 中可对腕奇异单独分支（θ4 取当前值、θ5=0 处理、θ6 按 ZYX 语义补算），而非直接丢弃整组解。

### C4 [D4-轨迹规划/控制联调] 如何把 planner 的梯形/S 曲线输出接入 movej 实现连续插补？有哪些实时性挑战？

**考察点**：跨层联调、实时系统思维。

**参考答案**：
- 现状：`robot_movej` 是点到点——角度经 `DEG2STEPS`（`角度°×减速比÷360×16384`）转脉冲，写 0x00D8~0x00D9 速度 + 0x00E8~0x00E9 绝对位置，电机内部跑完。
- 接入方案：planner 输出 `q(t)`（度），控制循环按周期 T 求 `q(kT)`，逐周期转脉冲写 0x00E8~0x00E9（立三支持**运行中执行**绝对位置，可逐点刷新目标实现轨迹跟随）；上位机负责速度/加速度整形，或部分依赖驱动器侧加减速（0x0098/0x0099 加速/减速时间）。
- 实时性挑战：
  - 单次 `modbus_transact` 超时 200ms、回零轮询 200ms，若插补周期远小于通信周期，会出现"目标点下发滞后 → 轨迹台阶"；
  - 需评估：6 轴轮询顺序与帧间隔、波特率是否够用、是否引入独立插补线程/双缓冲；
  - planner 本身纯数学、可离线单测（tests/test_planner.c），与通信节流解耦。
- 边界：到位精度由状态字 bit12（到位标识）或位置差判断；驱动器内部加减速与规划器轮廓叠加时需统一时间基准。

**追问方向**：梯形/S 曲线是关节空间规划，如何扩展到笛卡尔空间直线/圆弧（需 IK 每周期反解）？多轴同步如何保证？

**追问参考**：
- 笛卡尔空间直线：把 TCP 起点到终点的位置/姿态（平移+姿态变化）在时间上参数化（如按梯形/S 曲线对路径弧长 s(t) 规划），逐周期计算中间位姿（平移线性插值 + 姿态可用四元数/轴角球面插值），再经 IK 反解出 6 个关节角下发。每个插补周期都调一次 IK，计算量集中在 IK 与矩阵运算，PC 端充足，回单片机需评估周期预算。
- 圆弧：三点定圆/圆心半径法把弧长参数化，逐周期取弧上点并保持姿态方向（或绕弧法向旋转），同样 IK 反解；注意弧长与角度映射要均匀（按圆心角插值而非弦长），避免速度波动。
- 多轴同步保证：关节空间规划天然同步——每轴共用同一时间基准 t，轨迹同时开始同时结束；笛卡尔插补同理，同一 s(t) 驱动所有轴。难点在"反解出的关节角要平滑"：相邻周期 IK 解跳变（多解切换/奇异翻转）会产生关节速度尖峰，需在选解策略（ik_select_best 加权最近解）基础上加"解连续性约束"，必要时对关节角再做平滑滤波或重新规划。

### C5 [D5-架构/移植] 如果要把项目移植到单片机（无 Win32 API），需要改哪些文件？CommOps 如何帮助降低移植成本？

**考察点**：平台抽象、分层边界意识。

**参考答案**：
- 需要替换的：**只有 comm 层的 serial_win.c**（CreateFileA/DCB/COMMTIMEOUTS/PurgeComm/ReadFile/WriteFile 全是 Win32 API）。替换为 MCU 的 UART 驱动（如 STM32 HAL 的 UART_Transmit/UART_Receive），实现同签名 CommOps 实例即可。
- 不需要动的：modbus_rtu.c/h（帧构造/解析纯逻辑）、crc16、control 层全部（只依赖 comm_if.h 与 robot_internal.h 前向声明）、kinematics/trajectory/utils、tests（本就离线可跑）。
- 其他平台适配点：main.c 中 `SetConsoleOutputCP(65001)` 与工具里的 `Sleep`（可用 vTaskDelay 等替换）、logger 的 printf 重定向。
- 关键点：CommOps 无句柄参数、实现方自持全局状态，天然适配"单例外设"模型；`modbus_comm_set()` 注入点集中，换平台只改注入对象。
- 架构佐证：CMake 将 comm 独立成静态库，替换实现不触碰其他库目标。

**追问方向**：串口中断/轮询模式对 read_frame 语义的影响？如果 MCU 上要跑 RTOS，CommOps 的 read_frame 超时如何与调度配合？

**追问参考**：
- 中断 vs 轮询：轮询模式（当前 serial_win 风格）read_frame 阻塞直到超时或收到数据，调用方时间线简单但阻塞期间无法做别的；中断模式（MCU 常见）数据由 ISR/接收回调收进环形缓冲，read_frame 改为"等待队列/信号量，超时返回"——语义不变（返回一帧或超时），但实现要处理并发：环形缓冲的读写指针保护、临界区/关中断，防止 ISR 与主循环竞争。
- RTOS 调度配合：read_frame 不应忙等，改用信号量/事件标志等待——UART 收到完整帧（或帧间隔超时）后由驱动置位事件，read_frame 等待事件并带超时（vTaskDelay/带超时信号量），把 CPU 让给其他任务；超时参数由 task 的 tick 换算；flush 需原子操作（关中断/临界区）保证与 ISR 不冲突。
- 与 CommOps 的关系：接口不变、注入实现变化——PC 版"阻塞读+超时"、MCU 版"事件驱动+信号量等待"，control 层无感知，这正是抽象层的价值。多线程下 g_comm_ops 全局指针与串口句柄需加锁，避免读写交错。

### C6 [D6-调试排障/协议迁移] 项目从旧伺服方案切换到立三电机踩过哪些坑？如何防止协议混用回归？

**考察点**：协议迁移审计、防回归工程实践。

**参考答案**：
- 核心坑：**同地址不同语义**——旧伺服与立三寄存器地址逐地址冲突（如旧协议 0x0000 是状态字、立三 0x0000 是硬件版本），且外部资料不同源。误用旧协议地址读立三，**CRC 能通过但数据语义错误**（"安静的错误"最难排查），表现为状态/位置数值怪异而非通信失败。
- 其他差异：
  - 使能逻辑相反：立三 0x00D4 **写 0=使能、写 1=释放**（旧协议相反），误写会导致电机意外脱机/使能；
  - 无堵转寄存器：碰撞判定改为 0x001A 实时电流超阈值；
  - DWORD 字节序：低 16 位寄存器在前、字内高字节在前（旧协议体系不同）；
  - 回零速度寄存器：0x00D8~0x00D9（SV113 以下固件才用 0x009A）。
- 防回归手段：
  1. 所有寄存器地址收敛到 robot_internal.h 宏（`LEESN_REG_*`），**业务代码禁止裸寄存器地址**；
  2. 单测对齐立三手册示例帧（test_crc16 的 0xCA85/0x0DCA、test_modbus 的字节序/异常码/假串口往返），协议变更必回归；
  3. 审计清理旧协议残留（历史对话已完成），文档标注"旧协议已作废，不得引用"；
  4. 关键语义（使能/字节序）在头文件注释中写明契约与示例，防新人踩坑。

**追问方向**：如何设计一个"寄存器映射表"式的可配置层来隔离不同厂商协议？协议切换时哪些测试必须跑、哪些可跳过？

**追问参考**：
- 寄存器映射表设计：定义统一的"逻辑寄存器"编号（如 LOGICAL_POSITION/LOGICAL_STATUS/LOGICAL_ENABLE/LOGICAL_SPEED/LOGICAL_CURRENT），每厂商提供一张映射表（逻辑寄存器 → 该厂商物理地址 + 语义标志：字节序/使能极性/单位换算），modbus 层读逻辑寄存器时查表换算成物理地址，使能极性/字节序差异由适配层统一转换。更彻底的做法是"能力抽象"——不暴露寄存器，提供 set_speed/set_position/read_status 等语义接口，厂商差异全收敛在厂商适配模块内部。
- 必须跑的测试（协议切换回归）：①CRC 向量测试（test_crc16，换手册示例帧向量）；②帧构造/解析字节序测试（test_modbus，重点 32 位 DWORD 低字在前、异常码、坏 CRC）；③使能极性测试（新厂商使能语义是 0 还是 1，必须显式用例，防"逻辑相反"灾难）；④CommOps 假串口往返测试；⑤FK/IK/planner 纯数学测试（若只换电机，运动学/轨迹层应全绿——它们不依赖协议，可快速验证未受波及）。
- 可跳过的测试：不涉及协议层时（如只改 kinematics）可跳过通信测试；协议切换时运动学/轨迹测试理论上可跳过，但为防"改错头文件引入全局影响"仍建议跑一遍（CTest 全量很快）。核心原则：**字节序、使能语义、CRC 这三类最容易出"安静错误"的测试一条都不能省**。
