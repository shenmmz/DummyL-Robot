# DummyL-Robot 长期项目约定

## 用户对画直线的实际精度需求（2026-09-18 亲口确认）

**用户原话："之前我默认使用 sync 模式都不会画弧啊"** —— 指的是改成"逐航点等到位"
**之前**的那个 sync（定时注入版）。而那一版实测偏差 1.77mm ≈ 整段弓高 2.08mm，
**本来就是在画弧**，只是 2mm 在 50mm 线上视觉上看不出来。

⇒ **用户实际可接受约 2mm/50mm 的弓高**（约 4%），远宽于默认预算 0.10mm。
⇒ 现在的 smooth 模式 ≈ 用户之前习惯的观感。

**50mm 线的档位**（弓高 ∝ 段长²）：
| 预算 | 段数 | 弓高 | 卡顿 |
|---|---|---|---|
| smooth（1段） | 1 | ~2.0mm | 无（= 用户之前的体验） |
| 2.0mm | 2~3 | ~0.5mm | 很轻 |
| 0.5mm | 3 | ~0.23mm | 中 |
| 0.10mm（默认） | 5~10 | ≤0.10mm | 明显一顿一顿 |

**决定性旁证（用户 2026-09-18）**："跑 movej 很流畅，跑 movel 就一卡一卡"。
movej 是**单段**：一次下发、六轴按行程比例配速、驱动器各自梯形规划同时到达，
只有 1 次启动、无段间停顿。movel 分段后每段都要"减速到 0 → 下发 90ms 空档 →
重新加速"，且每段重复一次六轴启动差扭曲。
⇒ **流畅 = 单段交给驱动器规划**，这跟 Hg_Robot_Arm 的结论完全一致。
⇒ `smooth` 模式本质就是"会画直线的 movej"（代价是弧）。

**实测 4.55mm vs 几何弓高预测 0.39mm（差 11.6 倍）**：预测只算几何弓高，
漏了六轴启动差（首末轴相隔约 75ms）。启动差扭曲才是大头，且**段数越多扭曲次数越多**
⇒ 再细分不会更直，反而更糟。已把打印改成"几何弓高 ≤"并在实测超预测 3 倍时点破。

**已落地**：用户随后明确"弧小都比你一卡一卡的好" ⇒ 默认值已从 0.10 上调到 **0.50**
（`robot_config.ini` 的 `bow_mm` + 代码宏 `MOVL_SYNC_BOW_MM` 同步改，ini 优先）。
50mm 线由 5~10 段降到约 3 段，段间停顿次数减半以上，弓高约 0.23mm（看不出）。
**教训**：别拿实验室精度（0.1mm）当默认值去折磨实际使用——先问用户能接受什么。

## 总线事实（实测，勿再推算）

- 单事务 15.06 ms，其中等响应 14.85 ms（占 98.6%）；flush+write 仅 1.05 ms
- 一轮六轴 92.8 ms ⇒ 10.8 Hz；转换器吞吐只用了 12%（66 / 549）
- **连读六轴无批处理效应**：实测一轮 92.83 ≈ 推算 90.36（差 2.7%）⇒
  打包多寄存器读不会提速，瓶颈是"每笔都要等一次响应上行"，不是帧数
- 读写事务天花板 79 Hz（线上 1.82 ms + 3.5 字符间隔）
- **只写不等响应上界 159 Hz**——真实收益 14.7 倍（旧值 4.8 倍是被巡检污染的）
- CH340（VID_1A86&PID_7523）注册表**没有** LatencyTimer 项，
  "设备管理器改延迟计时器"这条路对本机不成立（那是 FTDI 的做法）
- 提速唯一现实路径：6 路独立 USB-RS485 + 只写不等响应（半双工下
  单总线不能背靠背写，noread 只在每总线单从站时安全）

## 线程模型与总线锁

- 串口是全局单例，后台巡检线程与主线程共用
- **总线锁在 `robot.c` 的 `robot_request` / `robot_request_noread`**，
  半双工下任何发送都必须持锁，与是否等响应无关
- 历史坑：`motor_write_i32_noread` 曾绕过锁，其 flush(PurgeComm) 冲掉
  巡检已收到的响应 ⇒ diag 刷假掉线。新增"快路径"务必检查是否绕过串行化
- `monitor_pause_active`：diag 已接；**运动路径（movej/movel）未接**，
  属安全取舍（挂起会丢失运动中堵转/报警监控），未获用户确认前不要擅自接

## 机械原点标定方法（用户 2026-09-21 亲口纠正，AI 之前理解错了）

**每个关节都有一个小凹槽，人工把六轴转到凹槽对齐 = 机械原点；对齐后程序应显示
`0,0,90,0,0,0`。** q0 的正确来源就是"对齐凹槽 → 读编码器 → 反算零点"。

**两个操作的本质区别（别再混）**：
- 跑 `home` 命令：程序堵转找限位 → 清零 → 退让 ⇒ 读数**必然**是定义值，**零信息量**
- **人手转凹槽对齐**：姿态由物理凹槽决定 ⇒ 读数是**测量结果**，**是有效标定**

⇒ 判断零点对错，先问"**你用什么外部参照判定的**"，答不上来才质疑；
  别拿 FK 自洽 / q2+q3+q5=180 去推断（那些恒真，证明不了任何事）。
⇒ 凹槽对齐是粗标（±0.5°~1°）；J5 差 1° ⇒ 笔尖偏 0.72mm。要更精可用水平仪微调。

## movel 的姿态参数（Rx,Ry,Rz）是"画斜线"的头号根因

`end_pose[0..5]` **全部取用户输入**，起点位姿由 FK 得。姿态不一致 ⇒ SLERP 把姿态
从起点一路拧到目标 ⇒ 中途姿态持续变 ⇒ 法兰下方笔尖绕法兰摆 `tool_length×sin(θ)`。

**实测（80mm 线，tool_length=41.17）**：姿态抄对 ⇒ 笔尖偏离 **0.0000mm**；
抄成 home 的 `115,90,115` ⇒ 偏离 **7.71mm**。而**法兰直线度恒为 0.0000mm**
⇒ **只看法兰坐标永远发现不了**。home 姿态 getpos 打印 `Ry=89.99`，绘图位姿是 `Ry=0`。

⇒ **movel 的 Rx,Ry,Rz 必须抄【当前 getpos】打印的原值，含负号、含 -0.00。**
⇒ 姿态恒定时 tool_length 只造成整体平移，**不会画斜线**（它只影响"坐标是谁的"）。
⇒ 已有防护：下发前 `movl_pose_warn()` 告警（阈值 `ini [movel] tip_warn_deg`，默认 5°）。
   离线自查工具：`build/bin/movl_tip_trace.exe J1..J6 X,Y,Z,Rx,Ry,Rz [tool_length]`。

## 法兰法线方向：home 是【水平】，绘图位姿才【竖直向下】（2026-09-21 rtb 实测）

| 姿态 | 关节角 | 法兰法线 n | 与竖直夹角 | q2+q3+q5 |
|---|---|---|---|---|
| home | 0,0,90,0,0,0 | **(+1, 0, 0) 水平指向 +X** | 90° | 90 |
| 绘图 | 0,0,110,0,70,0 | **(0, 0, -1) 竖直向下** | 180° | 180 |

⇒ **判据：q2+q3+q5 = 180 ⟺ 法线竖直向下（笔朝下，能画画的姿态）。**

**⚠️ getpos 的"歪了"对 home 是【误报】**：getpos 拿"法线应竖直"当通用标准，
但 home 是归零/收起姿态，法线本来就该水平。用户 2026-09-21 home 完看到
`法兰倾角 = 89.99°  歪了 (q2+q3+q5 = 90.01)` 问"为什么会歪，现在是正常的啊"
⇒ **用户是对的**。这个判据只适用于"笔要朝下"的场景，不该对 home 报警。
（措辞待改：或加一句"仅当笔需朝下时才有意义"。未获确认前不动 getpos。）

## 弓高只由【段长】决定（2026-09-21 离线复算坐实，可当公式用）

`弓高 ≈ 0.00089 × 段长² (mm)`，与模式名（sync/step/stream/smooth）**无关**。
段长 10/20/25/33/50/100mm ⇒ 弓高 0.09/0.35/0.56/0.97/2.20/8.94 mm。
已与 ini 里既有实测交叉验证（3 段 33.3mm ⇒ 实测 1.04mm，公式 0.97mm，差 7%）。

⇒ **当前驱动模式下"直"与"顺"不可兼得**（曾误判为"可兼得"，已推翻回来：
   那次用户看到的"直"是因为 smooth 根本没生效）。弯的是**位置**不是姿态
   （倾角全程 0.000°），别拿姿态指标判断直不直。
⇒ 唯一两全出路 = 驱动器**位置表**（#3d，段间不减速 ⇒ 可走密集弦）。
⇒ 离线算真实轨迹：`build/bin/movl_tip_trace.exe J1..J6 X,Y,Z,Rx,Ry,Rz [L] [line|joint]`
   （line = 笛卡尔直线插补；joint = smooth 单段关节空间插补）。

## second/ 框架与 Hg_Robot_Arm 对比（2026-09-21，实测坐实，别再重推）

`second/` = 按 Hg_Robot_Arm 移植的独立第二套框架（C 版），用于算法对比。
自检 `second/build/bin/t_hg_kin.exe`，CLI `second/build/bin/second.exe`（默认 dry run）。

**★ Hg 的运动学不能拿来控制本机**（判据是真机实测，不是模型自洽）：
home(0,0,90,0,0,0) → 真机 241.50/52.00/286.00；标准DH 逐位吻合；
**Hg 算出 241.500/0.000/338.000（Y−52、Z+52）**。
反过来拿真机位姿喂 Hg IK，8 组解最接近也差 **40.087°**。
根因：Hg 的 IK 用 `l_ew=√(115²+52²)=126.2`、`atan_e=atan(52/115)=24.3°`，
前提是「肘部偏置 52 与大臂共面」；**本机真机的 52 是平面外的（沿 z2，d3=52）**，
平面投影里只有 146 和 115。
**⚠️ 只改 FK 没用**：FK 掰对后 IK 结果一字不变、照样差 40.087°（IK 用 l_ew/atan_e，
与 FK 的连杆向量无关）。FK 与 IK 是自洽的一对，要改必须一起重推。

**★ Hg 的 MoveL 根本没有笛卡尔插补**（dummy_robot.cpp:737-835）：
一次 IK → 8 组解按限位过滤 → 挑 `Σ|Δθ|` 最小 → MoveJ。没有插补循环、没有中间航点。
⇒ 末端走关节空间弧，**就是主程序 smooth 模式的同一个东西**（100mm 弓高 8.70mm）。
"直 vs 顺"两条路线：Hg 选顺（1 次启停），主程序选直（分段逼近）。
⇒ 更说明 **#3d 驱动器位置表是唯一两全出路**。

**对接 Hg 时注意（别照抄数字）**：
- d6：Hg=183 是**装着夹爪**口径；主程序 91.5 = 法兰面（+tool_length 才是 183）。不是分歧。
- 姿态角分量顺序**相反**：Hg (A,B,C) = Rz(A)Ry(B)Rx(C)；主程序 (Rx,Ry,Rz) = Hg 的 (C,B,A)。
- 其余参数全同：140 / 35 / 146 / 115 / 52。
- Hg 原文有 ±π 缠绕 bug（该减 2π），`if (q>M_PI) q-=M_PI` 会把 200° 变成 20°。
- Hg MoveL 里那段"相对当前角 ±180° 归一化"是对的，别跟上面那条混为一谈。

## ⚠️ 逆解的 lastJoints：原文 MoveL 喂的是【全零】，不是当前角（2026-09-22 实测坐实）

`dummy_robot.cpp:757-761`：`Joint6D_t lastJoint6D{};` → 直接喂 `SolveIK`（那个变量后面才赋值）。
**lastJoints 只在腕奇异分支（cosqw=±1）参与计算**，而该分支有"把度当弧度"的 bug ⇒

```
同一位姿，只改 last：
  last = 0,0,0,0,0,0       → 解0 J4=   0.00  J6= 100.00   能执行      ← 原文行为
  last = 10,20,30,40,0,60  → 解0 J4=2111.83  J6=3257.75   8 组全越限，必失败
```

⇒ **判断逆解对不对，先确认 lastJoints 喂的是什么**。奇异位形下这一步决定"能不能动"。
⇒ 通式：`last` 只在奇异分支起作用，非奇异时八组解与 last 无关（实测解 2~7 完全相同）。
⇒ second 已修（`solve_pose(..., last)`，NULL=全零）。
