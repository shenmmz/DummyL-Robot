## 真机验证铁律
- 唯一标准是**读回来的实际值**；"命令没报错"不算。
- 顺序 `enable` → `getpos` → `alarm`。不 enable 时 getpos 是假数；失联时 getpos 打 `0,0,90,0,0,0` 假数 ⇒ 用 `alarm` 交叉验证；getpos 报"部分关节无响应"⇒ **禁止下发运动**。
- `alarm` 读 `0x00A3`（低4位=当前，高12位=最近三次），`alarm:clear` 写 `0x00A4=0`。报警未清 ⇒ 状态字 bit21=1 ⇒ 到位判据"已退出 RUN"永不成立 ⇒ 运动超时。
- **到位判据只有一份**（second 的 `leesn_inpos_query`，home/movej/movel/mj1 共用）：无报警 + 已退出 RUN + 位置在 target±tol 内。`STAT_INPOS`(bit12) 是**粘滞位**，只看它必假阳性（实测差 28.5° 也报"到位"）。
- 报警现状：J5 当前=电机相位过流；J1/J2/J3/J5 历史=供电电压过低。J5"一动就相位过流"未查清，别 clear 了当没事。

## movel「直 vs 顺」不可兼得
- 根因（手册 66 节⑤）：运行时收到新绝对目标**立即执行、当前指令强行结束** ⇒ 每段末独立加减速、**速度归零**。设计行为，换命令避不开。**段数 N = 归零次数 N**。归零耗时 = ACC+DEC = 80+90 = 170 ms。
- 卡顿模型：`额外耗时 = 固定收尾 0.32s + 段间停顿次数 × 每次停顿`（过流开 0.48s / 关 0.335s）。比值不能跨线长比较。
  ⚠️ **2026-09-23 待复核**：该模型是在"一轮六轴轮询 92ms(10.8Hz)"下拟合的，而读法修复后轮询变成
  10.2ms(97.9Hz) ⇒ "固定收尾 0.32s"里含的轮询延迟已缩小约 80ms。**这个系数要重测，别直接沿用。**
- **弓高 ≈ 0.001×段长²(mm)**；`段数 = ceil(sqrt(整段弓高/bow_mm))`；想让 L mm 内不分段：`bow_mm = 0.001×L²`（20⇒0.4 / 30⇒0.9 / 50⇒2.5 / 80⇒6.4 / 100⇒10）。
- 模式：`sync`（按 bow_mm 分段+逐航点等到位）/ `step`（1mm 弦）/ `stream`（不等+每节拍重设速度）/ `smooth`（1 段）。语法 `movel X,Y,Z[,Rx,Ry,Rz] [SPD,ACC,DEC] [keep][,模式]`。
- **2026-09-23 用户拍板默认改 `smooth`**（流畅优先）。代价①走关节空间直线（弓高=整段）②**全程不查过流** ⇒ 碰撞保护须显式 `,sync`。B 方案（stream 三要素）已判死。

## 驱动器 ACC/DEC
- `0x0096/97` 启停速度 50rpm；`0x0098/99` 加速/减速时间，值域 0~65535。实测六轴：启 0 / 停 0 / 加速 **80** / 减速 **90** ms（与反推 170ms 吻合）。
- `accel[:ACC[,DEC]]`，无参只读。只写 RAM 不发 `0x00DC` ⇒ 断电恢复。⚠️ 别发 `0x00DC=1`（固化），写 **0** 更是**恢复出厂**。太小丢步/过流，从 40 起试。

## 总线实测（并线接法，COM4）

### ★★ 2026-09-23 读法修复：单事务 15.4ms → 1.7ms（9 倍），此前所有"USB 延迟"结论作废

**根因**：`modbus_rtu.c` 原来 `read_frame(rx, sizeof(rx)=300, 50)`。
**ReadFile 请求的字节数 > 实际会到的字节数 ⇒ 不会因"读满"完成**，只能等
`ReadIntervalTimeout` 到期，而 CH341SER 把它挂在 **~15.6ms 节拍**上（= Windows 默认 64Hz
系统定时器）⇒ 每笔白等一个节拍。**与波特率、USB、驱动器全都无关。**
判据实验（同一笔读，只改 cap）：`cap=300→15.37ms`｜**`cap=9(正好一帧)→1.70ms`**｜`cap=10→15.17ms`｜`cap=64→15.44ms`。
**修法**：新增 `modbus_read_reply()` 分三段读，每段精确长度 ⇒ 每段立刻返回。
读类 `2→1(字节数)→n+2`；写类 `2→6`；异常应答 `2→1→2`。

**⇒ 作废的旧结论（别再引用）**：~~"T_usb ∈ [10.35,11.35)ms 占 67~74%，瓶颈在工具侧"~~、
~~"换转换器要换带延迟计时器的芯片"~~、~~"提波特率收益仅约一成"~~、~~"单事务 15.4ms"~~。
那 10~11ms 全是驱动定时器节拍，不是 USB 接收延迟。

**新基线（921600，2026-09-23 实测）**：

| 项 | 旧 | 新 |
|---|---|---|
| `diag` read / 单事务 | 15.43 / 15.60 ms | **1.63 / 1.70 ms** |
| `diag` 一轮 6 轴 ⇒ 刷新率 | 93.6 ms ⇒ 10.7 Hz | **10.2 ms ⇒ 97.9 Hz** |

**波特率现在才真正值钱**（同会话 A/B，`drvbaud` 临时切 115200 再切回）：
read `3.21→1.63ms`、一轮 `19.7→10.2ms`、刷新率 `50.8→97.9Hz` ⇒ **1.93 倍**。

### 驱动器波特率寄存器 0x0009（手册 §6，2026-09-23 查）
- 位域：低 8 位=**档位码**；bit9~8 校验（0无/1偶/3奇）；bit11~10 停止位（0=1位/1=0.5/2=2/3=1.5）。出厂 **12**（=0x000C=115200/8N1）。
- 档位表：1=300 2=600 3=1200 4=2400 5=4800 6=9600 7=14400 8=19200 9=38400 10=56000 11=57600 **12=115200 13=230400 14=460800 15=921600**。
- ⚠️ **没有 256000 这一档**。注意手册**第二章**"通讯速率与通讯距离"表里**列了 256000（250m）**，但那是**物理层速率-距离参考表**（证据：该表连 230400/460800/921600 都没列，是通用模板），**不是 `0x0009` 的可选档位**。§6 值域明确 **1~15**（15 个码已排满）⇒ **256000 写不进去**（写 16 超值域，别试）。已核对 PDF 原文第 2 页与第 9 页，与 md 一致。
- ⚠️ 写完**立即生效** ⇒ PC 侧不同时改就**当场失联**；6 台必须**广播一起写**（逐台写第一台就断了）。
- ⚠️ 不固化（`0x00DC=1`）则**断电回 115200**，而 ini 已是新速率 ⇒ 下次上电失联。所以改波特率**必须固化**——但 `0x00DC=1` 会把**所有**带记忆的 RAM 值一起写进 Flash（含 ACC/DEC），先调好再固化。
- 收益：115200→921600 线上 21B 共省 ≈1.6ms/笔。⚠️ **这个收益在 2026-09-23 修掉读法之前被完全掩盖**
  （当时每笔都要白等 15.6ms 驱动节拍）⇒ 修好后实测 **1.93 倍**（50.8→97.9Hz）。见上面"读法修复"。
- 命令 **`drvbaud`**（2026-09-23 新增，`commands.c`）：`drvbaud` 只读（六轴 0x0009 解码 + 固件版本 0x0002~0x0003）/ `drvbaud:CODE` 广播写（写完即失联）/ `drvbaud:CODE:BAUD` 写+切PC侧+回读验证（推荐）/ `drvbaud:save` 广播固化 `0x00DC=1`。**必须广播**（逐台写第一台就断）；不 save 则断电回 115200 ⇒ 试探可恢复。
- **2026-09-23 已实改：六轴全部 → 档位 15 = 921600**（广播写 + `0x00DC=1` 固化；`ini baudrate = 921600`）。固件版本读回 **21.9**。广播首轮曾漏 J1（回读丢帧），重启后六轴全 `15`。**固化把 ACC/DEC 30/30 一起写进了 Flash**（不再是出厂 120/120）。
- **实测收益（最终版，细节见上面"读法修复"）**：等响应路径 **1.93 倍**（50.8→97.9 Hz）；
  纯写吞吐 `busrate[3]` 1.05→0.15ms。**noread 已无意义**（13ms 比等响应 10.2ms 更慢）。
  ⚠️ 修读法**之前**测出的"等响应零提升"是假象（被 15.6ms 驱动节拍掩盖）⇒ 要复测波特率收益必须先修读法。
- 顺带修：`diag`/`busrate`/`nrtest` 的判读文案原本**硬编码 `MODBUS_BAUDRATE`(115200)**，改 ini 后会打印自相矛盾的判读 ⇒ 已改成读 `serial_get_baud()`。

## RS485 工具（looptest，见测试 22）
- ⚠️ **本节的"驱动器侧耗时"公式与 T_usb 结论已作废（2026-09-23 读法修复）**：
  `接电机单事务 15.4ms − 回环 RTT = 驱动器侧耗时` —— 那个 15.4ms 里约 13.6ms 是
  `modbus_transact` 用 `cap=300` 读导致的**驱动节拍等待**，根本不是线上/驱动器/USB 的耗时。
  ~~T_usb ∈ [10.35,11.35)ms~~ 与 ~~"换工具要换带延迟计时器的 FTDI/CP210x"~~ **都作废，别据此换硬件。**
- **为什么当年没看出来**：looptest 自己用的是**精确长度**读（`need = LOOP_FRAME_LEN`，
  commands.c:3280 附近），所以它的回环 RTT **从没吃到那个 15.6ms 节拍**；而 modbus_transact
  用的是 `cap=300` ⇒ 两边 ReadFile 的等待量不同，**这个减法消不掉噪声，反而把噪声当成了结论**。
  ⇒ 教训：**A/B 两侧必须用同一种读法**，否则差值里全是测量方式的差异。
- looptest 的测量逻辑本身仍然有效，`[2]` 连发推帧 = **1.12ms/帧 ≈ 892Hz**（与 `busrate[3]` 同量级）⇒ 写方向没问题。
- `looptest[:N[:BAUD[:AUX]]]`：① 单模块（A/B 悬空）② 双模块（给 AUX 口名，如 `looptest:30:0:COM5`）。
- **物理事实**：A/B 是差分对，**同一端口内 A-B 短接 ⇒ 差分恒 0 ⇒ 一字节都收不到**（还短路输出）。回环要求 A/B **悬空**。
  - 本机 CH340 单模块实测：三种 RTS 各 3 次**全 0 字节** ⇒ 该模块发送时关接收，单模块**测不出 RTT**，只能上双模块。双模块必须 **A-A / B-B 对接 + 共地**；短线（<1m）不要加 120Ω。
- ⚠️ 命令自动恢复波特率/RTS/关闭辅口；RTS 停在 ENABLE 会让六轴全"离线"。
- ⚠️ 术语坑：用户说"A 与 B 接一起"指**标准多点总线**（所有设备 A 连一起、B 连一起），**不是**同端口 A-B 短接。

## 驱动器表格数据 / 编程区（A 方案）
- `0x00AA` 表大小 / `0x00AB` 指针 / `0x00AC` 表起始(=实际−300，编程区≥300，32位/个) / `0x00DD` 执行 / `0x00DC` 保存（写1保存，**写0=恢复出厂**）/ `0x00DB` 执行编程命令 / `0x00D6` 实时速度 0.01rpm(RO)。
- 手册 54 节"每次执行完指针减 1" ⇒ **写一次 `0x00DD` 只执行一个数据点** ⇒ 省不掉总线往返，**A 方案不成立**。真要连续走须靠 `0x00DB`（写 V ⇒ 执行位置 V+299；写 1 ⇒ 从 300 开始；配套 `0x0015`/`0x0075`/`0x0076,77`/`0x0078,79`），但**手册缺"编程指令格式"章节 ⇒ 向厂家索取**。
- `tabtest` 判据：执行后读位置，算"一次 0x00DD 走了几段"。

## cmd_parse 坑（已修）
- 症状：非法参数打警告后**命令照样执行**（`busrate:7` 跑了一整遍）。根因：分支**先设 `out->type` 再校验**，失败 `return CMD_UNKNOWN`，但 `main.c` **只看 `cmd->type` 不看返回值**。
- 修法：入口 `memset(out,0,...)` + 46 处先复位 type 再返回。`line==NULL||out==NULL` 那处**不能**写 `out->type`。新增命令：`out->type` 要么放全部校验之后，要么保证失败时复位。

## 机械原点与标定
- 每关节小凹槽，**人工对齐 = 机械原点**，应显示 `0,0,90,0,0,0`。q0 正确来源 = 对齐凹槽 → 读编码器 → 反算零点。跑 `home` 是堵转清零 ⇒ 读数**必然是定义值、零信息量**。判零点先问"用什么外部参照判定的"。
- 凹槽对齐粗标 ±0.5~1°；J5 差 1° ⇒ 笔尖偏 0.72mm。
- 堵转阈值疑似偏低：静止电流 ~500/499/495/385/371/254mA vs 阈值 480/490/480/400/390 ⇒ J1/J2/J3 一上电就"已堵转"。未证实。

## movel 姿态参数是"画斜线"头号根因
- `end_pose` 全取用户输入，起点由 FK 得；姿态不一致 ⇒ SLERP 拧姿态 ⇒ 笔尖绕法兰摆 `tool_length×sin(θ)`。80mm 线实测：抄 getpos 原值 ⇒ **0.0000mm**；抄 home 的 `115,90,115` ⇒ **7.71mm**。法兰直线度恒 0.0000mm ⇒ **只看法兰坐标永远发现不了**。
- **必须抄【当前 getpos】原值，含负号、含 -0.00**。防护 `movl_pose_warn()`（ini `[movel] tip_warn_deg` 默认 5°）；离线自查 `build/bin/movl_tip_trace.exe`。
- 法兰法线：home 水平(q2+q3+q5=90)，绘图位姿竖直向下(=180)。getpos 拿"法线应竖直"当通用标准 ⇒ **对 home 是误报**（用户 2026-09-21 确认），未获确认前不动 getpos。

## second/ 与 Hg_Robot_Arm
- `second/` = 按 Hg_Robot_Arm 移植的第二套框架；自检 `t_hg_kin.exe`，CLI `second.exe`。**不许有名为 `src` 的文件夹**，源码平铺 `second/include/`。
- **Hg 运动学不能控制本机**：home 真机 241.50/52.00/286.00 vs Hg 241.500/0.000/338.000；喂真机位姿给 Hg IK 最接近差 **40.087°**。根因：Hg IK 假设"肘部偏置 52 与大臂共面"，**本机 d3=52 在平面外** ⇒ **FK/IK 必须一起重推，只改 FK 没用**。
- **Hg 的 MoveL 没有笛卡尔插补**（dummy_robot.cpp:737-835）：一次 IK → 8 解过滤 → 挑 `Σ|Δθ|` 最小 → MoveJ = 主程序 `smooth`。
- 对接 Hg 别照抄数字：d6 Hg=183 是夹爪口径（主程序 91.5=法兰面）；姿态角分量顺序**相反**（Hg (A,B,C)=Rz(A)Ry(B)Rx(C)）；原文有 ±π 缠绕 bug；逆解 lastJoints 原文喂全零、腕奇异分支(cosqw=±1)有"度当弧度"bug（second 已修）。
- A/B 对照台 `second/tests/hgref/`：`build_ref.sh` 编 Hg 原文 exe，`ab.sh` 对拍 68 项；奇异位形两边都吐 2111.83/3257.75 才算连 bug 都抄对。
- **±180° 分支切割**：float vs double 挑到相反代表值（下发差 360°=50 圈）⇒ 比对角度**必须取模**。

## 其他
- 用户面角度一律**机械角**：`forward_deg[j] = 目标机械角 + q0[j]`；`red={50,100,50,50,50,50}`（J2=100），`DEG2STEPS(deg,red)=deg×red/360×10000`。
- `0x00E8` 是绝对目标；运行中写入 = 立即执行 + 强行结束当前指令 ⇒ 起点记错不会走错，只有**配速**会错（表现为超时未到位）。`0x0066` 不是通信地址来源（实测地址 2/3）。
- 已排除寄存器：`0x00B6/B7` 动态定位(IO 触发)、`0x009F` 运行模式(外部脉冲)、`0x00D0` 运行到绝对位置。IK 实测 **<40µs/次**，不是瓶颈。
- **决策文档：`docs/运动流畅性提速路线.md`**（2026-09-23 读法修复后整体重写）：
  A 调 ACC/DEC 零风险 ｜ ~~B noread 快发~~ **已作废**（修读法后 noread 13ms 比等响应 10.2ms 更慢）｜

## ★ 读法修复后新冒出来的两个瓶颈（都未改，属运动/安全行为变更）

- **`MOVEJ_POLL_MS = 10`**（commands.c:38，到位轮询的 `Sleep`）：修读法后它**占了轮询周期一半以上**
  （6 轴待读 10.3+10=20.3ms；只剩 1 轴 1.7+10=11.7ms）。降到 1~2ms 还能再快 **1.8~4 倍**。
  ⚠️ 属运动行为变更，验收要上真机用 50mm 线测"段间停顿"⇒ **须先 `home`**（现在 J1 越软限位、
  零点很可能已丢，MoveL/MoveJ/curtest 全锁着，动不了臂）。
- **`MONITOR_DEFAULT_INTERVAL_MS = 300`**（monitor.h:41）：巡检一轮从 185ms 降到 20ms ⇒
  周期 485→320ms。改 100ms ⇒ 周期 120ms（**堵转/碰撞反应快 4 倍**），总线占用 17% 仍远低于修复前的 38%。
  ⚠️ 安全参数，未擅动。
- `looptest` 的模型常量已重写（`LOOP_REF_WITH_MOTOR_MS` 15.4→1.70、`LOOP_GAP_MS` 4.00→2.00、
  新增 `LOOP_T_DRV_MIN_MS=1.39`）：旧版会印"工具接收路径 ≥10.35ms、占 67%、要换 FTDI/CP210x"，
  **是有害的错误结论**。新结论 **T_drv ∈ (1.39,1.92] ms、USB 栈 ≤0.08ms ⇒ 大头是驱动器处理时间**，
  换工具/再提波特率只剩约 13% 空间。
- ⚠️ 通用教训（写进了 looptest 注释）：**A/B 两侧必须用同一种读法**。当年 looptest 自己用精确长度读、
  而 `modbus_transact` 用 cap=300，两边等待量不同，那个减法消不掉噪声，反而把噪声当成了结论。
