## 卡顿的真正物理量（本次梳理清楚，可当模型用）

**段间速度凹陷：深度 = 全速、宽度 ≈ ACC+DEC、次数 = 段数-1。**
⇒ 想减轻顿挫只剩一条路：减小 ACC/DEC ⇒ 段长下限（= `seg_ramp_ratio`×(ACC+DEC)）
跟着降 ⇒ 段数变多，把"3 次深而宽的凹陷"换成"十几次浅而窄的凹陷"。
不能消除，只能压到人不易察觉。**完全无凹陷只有 1 段（smooth）**，代价是弓高。

## ★★ 卡顿的【客观指标】：sync 的"实际耗时/预计耗时"（新增打印）

**为什么它有效，而 stream 的同一比值无效（别混用）**：
- `sync` 的 `sync_rpm` 由 `total_dt` 反推，`total_dt` 是 `line_time_table` 按 vmax
  **匀速**算的，**不含**段间"减速到0→重新加速"的时间 ⇒ 实际耗时实打实超出预计，
  超出的部分就是归零吃掉的。**比值 = 卡顿指标。**
- `stream` 的段时长做过梯形斜坡补偿（ACC+DEC 已算进预计）⇒ 归零被藏进预计，
  实测 1.007 而用户照样卡（ini 有记录，已坐实）。⇒ stream 的比值不能证明流畅。

**物理模型**：`卡顿不适感 ≈ (段数−1) × (ACC+DEC)`。
两个旋钮**独立**：`bow_mm` 改归零**次数**，`acc_floor_ms` 改每次归零**宽度**（段数不变）。
⇒ "又直又顺" = 够多的段数(直) × 够窄的凹陷(顺)。

**代码**：新增 `sync_finish(t0, total_dt)`（commands.c:1158），替换 sync/smooth 的
3 个 `dev_report("sync ")` 退出点；块内加 `uint32_t sync_t0`。
⚠️ 用脚本批量替换时**会连函数体内部那句也替换**（4 处而非 3 处）⇒ 无限递归，
已修回 `dev_report("sync ")`。以后批量替换要注意。

**测试卡**：`docs/测试方法与验收标准.md` → **测试 16**（四档扫描 A smooth / B 默认 /
C acc_floor=20 / D bow=0.5+acc20）。及格线：直 ≤1.0mm(100mm线)、顺 比值 ≤1.15。
判定关键：C 与 B 比，偏差应基本不变、比值应下降。

## ★★★ 2026-09-23 真机实测（94.8mm 线，sync 3 段）—— 卡顿拆解

`movel:150,2,114,-180,0,-180,70,80,90`（SPD=70 ACC=80 DEC=90，姿态 -180,0,-180）
```

```
用户评价："还好，不画弧线，唯一就是停顿3次"。

**额外 1.28 s / 2 次段间停顿 ≈ 640 ms/次，拆解（估算，与总量吻合）**：
| 组成 | ms |
|---|---|
| 过流检查 6 轴读电流 | ~183 |
| 下发六轴目标+速度 | ~90 |
| 等到位轮询粒度 | ~160 |
| **驱动器归零+重启（=ACC+DEC）** | **~170** |
| 合计 | ~603 |

**★ 重大修正：归零只占 27%，大头 73% 是每段的固定总线开销。**
ini 里"卡顿根因=驱动器每段归零"这个说法**不完整** —— 归零决定"顿的深度"，
程序开销决定"顿的时长"，两者独立，得分开治：
- **降比值（顿的时长）**：关过流检查 / 减小轮询开销 —— 不动段数、不影响精度
- **降次数（顿的次数）**：减少段数（调大 bow_mm）—— 代价是弓高变大

**⇒ 比值这个指标只衡量【程序开销】，不衡量【归零次数】。用的时候别混。**
（这解释了 stream 比值 1.007 却照样卡：它没程序开销，但归零次数多。）

**弓高实测 vs 预测**：94.8mm 线 3 段，预测 ≤1.08mm、实测 0.86mm ⇒ 实测约为预测的 80%，
几何弓高公式偏保守，可以按预测值打 8 折估实测。

**段数反推公式（已用本次数据验证）**：
`target_n = ceil(sqrt(bow_full / bow_mm))`，bow_full = 整段弓高
- 本次：bow_full=9.52、bow_mm=2.0 ⇒ ceil(sqrt(4.76))=ceil(2.18)=**3** ✔ 与实测一致
- 要 2 段：bow_mm ∈ (2.38, 9.52] ⇒ 取 **4.0**（预测弓高 2.38mm，实测估 ~1.9mm）
- 要 1 段：= smooth（9.52mm）

## 【追加】新增 busrate 命令 + 修掉一个通用解析 bug（2026-09-23 下午）

### 1. 新增 `busrate[:N]` —— 回答"这根 485 最高多少 Hz"

`cmd_busrate()` 在 `src/cli/commands.c`（cmd_tabtest 之后），五档一次跑完，高精度计时
（QueryPerformanceCounter）。**探针 = 把 0x00D8 写回读到的原值 ⇒ 电机不动、速度不变**
（不用"写当前位置"：位置读错成 0 就是甩臂）。前置：重新编译重启，无需 enable/home。

**真机实测（并线接法，115200 bps，三次复跑一致）**：
```
[1] 单轴 读位置              15.4 ms/次     65 Hz
[2] 单轴 写 + 等响应         15.3 ms/次     65 Hz
[3] 单轴 只写不等响应         1.05 ms/次    948 Hz    ← 推帧时间
[4] 六轴一轮 只写不等响应     6.73 ms/轮    148.7 Hz
[5] 六轴一轮 读位置          93.6 ms/轮     10.7 Hz   ← 当前整机更新率
```
- 等响应占单事务 **93%**。
- **[3] 的含义要小心**：1.05ms 就是 13 字节 @115200 的线上时间 1.13ms ⇒ **WriteFile 是
  "等帧发完"才返回，这是物理下界，没法再快**。但它**不是可用的更新周期** ——
  半双工下从站仍回一帧（8 字节 ≈0.7ms）占线，再加驱动器处理 ⇒ 独立总线真实周期
  预计 **2~5ms（200~500 Hz）**。想直接吃 948 Hz 必须让从站不回帧 ⇒ 广播（`bcast`）。

### 2. ⚠️ 修掉一个**通用**解析 bug：非法参数照样执行

**症状**：`busrate:7` 打印警告后**仍然跑了一整遍 busrate**。
**根因**：`cmd_parse` 若干分支**先设 `out->type = CMD_XXX` 再校验参数**，失败时
`return CMD_UNKNOWN`，但 **`main.c` 只看 `cmd->type`、不看返回值** ⇒ type 已被改成有效命令。
**影响面 46 处**（home/movej/movel/curtest/stall/tabtest/busrate… 都有）。
**危险案例**：`movel:150,2,114,abc` 此前会**带着脏值下发运动**。
**修法**：① 入口 `memset(out, 0, sizeof(*out))`（CMD_UNKNOWN=0）
② 46 处 `return CMD_UNKNOWN;` → `{ out->type = CMD_UNKNOWN; return CMD_UNKNOWN; }`（加花括号保语义）
③ `line==NULL || out==NULL` 那处**不能**写 `out->type`（空指针，替换时踩到过）。
验证：`busrate:7/x/1:2/0` 四条只打警告；`busrate:2` 正常跑。ctest 12/12。

### 4. 排除掉的寄存器（别再看）

- `0x00B6/0x00B7`「设置动态定位」= 输入口(X0~X14)触发跑 N 个脉冲，**与串口改目标无关**

- `0x00D0`「运行到绝对位置（仅停止时可执行）」vs `0x00E8`「运行或停止都可执行」⇒ 我们用的 0x00E8 正确

## 14:20 ★ 结论修正：提波特率不是"零收益"，收益在 noread 快发路径

## 15:00 ★★ 找到并修掉真正的瓶颈：`ReadFile` 请求字节数过大 ⇒ 每笔白等 15.6ms 驱动节拍

**用户问**："你代码是不是加延时了呢，为什么会出现 read = 15.43ms，write = 0.15ms"
**答**：代码里**一处 Sleep 都没有**（读路径 grep 过，Sleep 只在注释里）。15.43ms 全在 `ReadFile` 内部。

**根因**：`modbus_transact` 用 `read_frame(rx, sizeof(rx)=300, 50)`。
**请求的字节数 > 实际会到的字节数时，ReadFile 不会因"读满"而完成**，只能等
`ReadIntervalTimeout` 到期；CH341SER 把它挂在 **~15.6ms** 节拍上（= Windows 默认 64Hz 系统定时器）。
⇒ 与波特率、USB、驱动器全都无关。这就是"提波特率没效果""换转换器没效果"的真原因。

**探针实测**（Python ctypes 直调 Win32，一次性脚本放 `%TEMP%\rs485probe\`，不进仓库）：
同一笔读 `01 03 0004 0002`，只改 ReadFile 的 cap：

| cap | 平均 |
|---|---|
| 300（旧代码） | 15.37 ms |
| **9（正好一帧）** | **1.70 ms** |
| 10（多 1 字节） | 15.17 ms |
| 64 | 15.44 ms |
| 非阻塞轮询 | 1.61 ms（首字节到达也是 1.6ms） |

非阻塞轮询证明**回帧 1.6ms 就到齐了**，是 ReadFile 不肯返回。

**修法**：新增 `modbus_read_reply()`（`src/comm/modbus_rtu.c`），分三段读、每段精确长度：
读类 `2 → 1(字节数) → n+2`；写类 `2 → 6`；异常应答 `2 → 1(异常码) → 2`。

**真机验证（COM4，六轴在线，921600）**：

read `3.21→1.63ms`、一轮 `19.7→10.2ms`、刷新率 `50.8→97.9Hz` ⇒ **1.93 倍**。
⇒ **读法修好后 921600 才第一次真正值钱**；修之前测出的"零提升"是被节拍掩盖的假象。

## 15:1x 用户点破根因：**"之前用 CAN 通信就没这个问题"**（重要背景）

用户原话："是通信架构这个一问一答拖累了。之前我是使用 can 通信，就没有出现这个问题。"

**用户说的"之前"= 参考项目 Hg_Robot_Arm**。本项目 `second/include/plan.h:10-11` 自己写着：
> "不搬：**CANopen**/步进电机的下发、FreeRTOS 互斥量、osDelay"
> "执行层换成 leesn.c（**本机是立三 LEESN 步进，不是原版的 CAN 伺服**）"

⇒ **CAN 是原版的；本机是立三 LEESN 步进 + RS485/Modbus-RTU。** 这正是差异的来源。

**CAN 为什么天生没有"1.47ms 周转"这一项**（三条，都不是"线更快"）：
1. **ACK 是硬件 1 bit**，塞在数据帧的 ACK 槽里，**不额外占报文时间**；
   而 Modbus 的"确认"是**一整帧 13 字节响应报文**，且必须等从站处理完才发。
2. **CAN 从站可以主动周期上报**（PDO / 广播）；Modbus-RTU 从站**不主动说话**，必须主站问。
3. **连发不等响应**：CAN 控制器的仲裁/CRC/重传由**硬件**负责，主机连发下一帧无需软件等 `ReadFile` 返回。
⇒ CAN 上那 1.47ms **不是被优化掉，是协议设计里根本没有这一项**。

**比特率其实差不多**（921600 bps ≈ 1 Mbps CAN），差的是**每笔要不要等**：
- CAN 标准帧（11 位 ID + 8 字节负载）≈ **130µs/帧**（含约 47 bit 开销）
- Modbus 单笔 21 字节 = 0.23ms 线上，**但 + 1.47ms 周转 = 1.70ms**
⇒ 换 CAN 后瓶颈会从"**协议等待**"转移到"**驱动器自己的控制周期**"（通常 1ms 或 125µs）。

**⚠️ 用户自己的文档早就记过这件事**：`docs/画直线与总线提速任务清单.md:189`
> "原来'想变直只能提速总线'的推论不再成立，**换 CANopen/EtherCAT 的紧迫性下降**"

原因：真正拖慢的**不是 Modbus 协议，是那个 15.6ms 读 bug**（已修，9 倍）。修完之后 Modbus 才暴露出它真实的上限 98.1 Hz。

## 15:2x **已实施：把 11 处 320ms 盲等换成事件握手**（用户拍板"帮我修改一下"）

### 旧代码为什么必须盲等
`monitor_pause_active(1)` 只置 `m->paused` 标志；监控线程的循环是 `poll → Sleep(interval)`，
**标志只在下一轮循环开头才被看到** ⇒ 调用方无法知道它何时醒，只能睡满「一个周期 + 一轮巡检」= 320ms。

### 新机制（`monitor.c` / `monitor.h`）
- 新增字段：`volatile LONG parked;` + `HANDLE wake_ev;` + `HANDLE parked_ev;`（均 `CreateEvent(NULL,FALSE,FALSE,NULL)` 自动复位）。
- 线程循环：`Sleep(interval)` → **`WaitForSingleObject(wake_ev, interval)`**（可被立即打断，不再干睡 300ms）。
  - 未挂起：`parked=0` → `monitor_poll()`
  - 已挂起：`parked=1` → `SetEvent(parked_ev)`
- `monitor_pause()` 额外 `SetEvent(wake_ev)`（立刻打断线程的等待）。
- `monitor_stop()` 额外 `SetEvent(wake_ev)`（线程立刻退出，不必等超时）。
- `monitor_start()` 额外复位 `paused=0` / `parked=0` —— **这是安全性加固**：历史上"挂起后漏恢复"会让巡检永久停住，
  而 `home` 会 `stop → start`，若 `paused` 残留 1，重启后监控就再也不会巡检了。
- 新增 API：
  - `void monitor_park(void);` = `monitor_pause_active(1)` + 等后台真停住（drop-in 替换旧两行）
  - `int monitor_park_wait(int timeout_ms);` —— 返回 1=已停住 / 0=超时（打警告并按旧行为继续）
  - 超时用 `MONITOR_PARK_TIMEOUT_MS 500u`：**兜底路径行为等同旧的盲等，零回归风险**。
- `monitor_park_wait` 用**轮询 `parked` 标志**而不是只信事件（自动复位事件可能残留旧信号）：
  循环 `检查 parked → 检查超时 → WaitForSingleObject(parked_ev, 剩余)`，被伪唤醒就再检查一遍。
