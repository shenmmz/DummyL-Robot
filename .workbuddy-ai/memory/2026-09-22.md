## 修掉：MoveL 的 lastJoints 传错（撞腕奇异就必然失败）

**现象**：second 的 `movel` 一遇腕奇异就报"8 组解全部越软限位"，臂不动。

**根因**：原文 `dummy_robot.cpp:757-761` 是
```
DOF6Kinematic::Joint6D_t lastJoint6D{};          // 零初始化
dof6Solver->SolveIK(pose6D, lastJoint6D, ikSolves);   // 喂进去的还是全零
```
（那个变量是后面打分循环里才被赋值的。）second 的 `plan_movel` 却喂了**当前关节角**。
lastJoints **只在腕奇异分支（cosqw=±1）参与**，而该分支有"把度当弧度"的 bug ⇒ 喂当前角就爆炸。

实测（同一位姿 275.541,48.585,508.580,49.568,-7.644,106.466，只改 last）：
```
last = 0,0,0,0,0,0       → 解0 J4=   0.00  J6= 100.00   在限位内，能执行   ← 原文
last = 10,20,30,40,0,60  → 解0 J4=2111.83  J6=3257.75   8 组解全越限，必失败
```
解 2~7 两种 last 完全相同 ⇒ 只影响奇异那两组，与"lastJoints 只在奇异分支用"吻合。

**修法**：`solve_pose(x,y,z,a,b,c, solves, const double *last)`，传 NULL = 全零。
`plan_movel` / `plan_show_solves` / CLI `ik`（默认）全用全零；`ik` 可显式覆盖（A/B 需要）。
**顺带修**：`plan_show_solves` 原先在归一化前也判一次限位，会把 plan_movel 实际接受的解
显示成"越限"。改成只在归一化后判（与原文 :767-779 一致）。

## 【重要】q0 与 HOME_MECH 的对应关系：J3 上有个 90°，用软限位判据定死 = 代码对

用户口径：「{0,0,90,0,0,0} 是建模之后的角度值，q0 那组（电机角）的姿态对应着 {0,0,90,0,0,0}」。
按代码约定 `机械角 = 电机角 − q0` 代进去：电机角 = q0 ⇒ 机械角 = **{0,0,0,0,0,0}**，
**不是 {0,0,90,0,0,0}** ⇒ 只在 J3 上差 90°。

**判据（决定性）：J3 的机械角软限位是 [30, 180]**（cfg.h JOINT_LIMIT_MIN/MAX）。
- 若机械原点 = mech {0,0,90,0,0,0} ⇒ J3=90，**在限位内 ✓**
- 若机械原点 = mech {0,0,0,0,0,0} ⇒ J3=0，**低于下限 30 ✗，回零后根本不能动**

## 手册关键事实（SV126，已查证，别再猜）

- `0x00C8` 取值：0=减速停止，1=正向运行，**256(0x0100)=急停**，257=反向运行
- `0x00C9` = 回原点执行寄存器（WO）—— 驱动器自带回原点功能，尚未研究
- `0x00D0~D1` = 运行到绝对位置（**仅停止时可执行**）；`0x00E8~E9` = 运行到绝对位置（**运行或停止都可**）
- **`0x00D2~D3` = 设置当前电机位置，手册 §67 给了 WriteDWORD 写示例，但【总表标 RO】** ← 自相矛盾，正是"伪清零"疑点

- 协议文档 §8.2 推荐的回零时序：**急停(0x00C8=0x0100) → 清零(0x00D2~D3=0) → movej**
  （second/src 用的是 减速停止 0x00C8=0，与文档不一致 —— 待议）
- 字序（手册示例坐实）：`0x00E8` 存**低16位**、`0x00E9` 存高16位 ⇒ 与 src/second 的
  `vals[0]=low, vals[1]=high` 一致 ✓（-8000 示例帧 E0 C0 | FF FF）

## 连发三条 movej「不对啊」——根因与修复（已修）

**内部 current 是「上次下发的目标」，不是「实到」。**

## ⚠️ STAT_INPOS(bit12) 是粘滞位 —— 到位判据必须查位置（重要，会假阳性）

**现象**：`movej ... go` 打 `[等待] 全部到位，用时 0.6 s`，实际 J2 还差 28.5°。
**根因**：判据写成 `((st&STAT_RUN_MASK)!=STAT_RUN_ACTIVE) && (st&STAT_INPOS)`，
只看状态位。bit12 是**粘滞位**：上一段运动结束置上后，新指令真正启动前不清；
此刻 RUN 位也没翻 ⇒ 读到"没在跑+已到位" ⇒ 假成功。

**唯一正确判据**（home_inpos_query 一直这么写，所以回零从没假阳性）：
无报警 + 已退出 RUN + **位置在 target±tol 内**。
⇒ 已提为 `leesn_inpos_query(joint,target_steps,tol_steps)`，home/movej/movel/**mj1** 共用。
**mj1 之前用的是同一套错误判据 ⇒ 这个"单轴隔离工具"一直是坏的。**

**换算常量（可直接用）**：red={50,100,50,50,50,50}；q0={-176.70,74.60,-180.07,4.29,113.67,84.89}
steps = (机械角+q0)*red/360*10000；关节°/s = rpm/red*6。
例中 J2 目标 0°=207222 步，当前 29.197°=288324 步，Δ=-81102 步；J3 目标 90°=-125097，
当前 61.004°=-165369，Δ=+40272。

**待查（下次上机第一件事）**：J2/J3 在 0.6 s 只走了 0.682°/0.761°，

## src 的 movel 为什么卡顿且不直 —— 与 second 的差异分析（2026-09-22，仅分析未改码）

**根因一句话：src 做笛卡尔插补（切 N 段），second 不做（整段一次 IK，1 段）。**

**卡顿来源（src sync 每发一段，commands.c:2138-2166）**：
| 步骤 | 事务 | 耗时 | 轴状态 |
|---|---|---|---|
| movl_stall_guard 过流保护 | 6 读 | ~90ms | 停着 |
| movl_set_seg_speed 按段重设速度 | 6 写 | ~90ms | 停着 |
| movej_issue_noread 连发位置 | 6 写 gap4ms | ~26ms | 启动 |
| movej_wait 等到位 | ≥1 轮 | ~100ms/轮 | 在动 |
⇒ 段间纯死区 ~200ms 且**速度真的归零**（movej_wait 判据=位置进容差，梯形规划走完即为 0）。
second 只有 1 次下发 ⇒ 零空档。**这就是"流畅感"的全部来源。**

**不直的来源：段数越多越歪（U 形，不是单调）**
50mm 线：段数 1/2/3/5 ⇒ 实测偏差 2.11/1.26/1.59/**4.59** mm（几何弓高 2.08/0.37/0.24/0.39）。
段数↑ ⇒ 几何弓高按平方↓，但**段间六轴启动差扭曲次数线性↑**（首末轴相隔约 75ms，
noread 后约 26ms）⇒ 5 段实测是几何预测的 11.9 倍。
second 单段 = 上表"1 段"那行：偏差 ≈ 纯几何弧，**没有启动差扭曲** ⇒ 看着是条规整的弧。

**⚠️ src 已有 smooth 模式 = second 的行为（target_n=1，commands.c:2057-2061）**，
且 2026-09-19 修过 bug：smooth 以前是死代码，掉进 step 路径被切成 101 段。
默认模式是 SYNC（cmd_parser.c:289），ini [movel] bow_mm=2.0。
⇒ 先确认用户跑的是哪个模式再谈改。

**其它 src 独有开销**：过流保护每段 6 笔读（安全换流畅的取舍，[stall] 阈值生效中）；
按段重设速度（2026-09-18 修的 bug：旧写法用整段位移比定速 ⇒ J2/J3/J5 提前到位停住
⇒ 甩成弓形 1.9mm，保留是对的）；MOVL_ACC_FLOOR_MS=60 加减速下限。

## 概念澄清（用户提问，2026-09-22）：插补的意义 / 两级段数

**插补的意义**：驱动器只认"目标关节角 + 自己梯形规划"，**不懂末端直线**。
MoveJ = 六轴角度各自线性插值 ⇒ 笛卡尔空间走弧。要末端走直线只能上位机把直线
切成一串点、逐点 IK、依次下发 ⇒ 这就是插补。弓高 ∝ 弦长²，弦长减半弓高变 1/4。

**⚠️ src 里"分段"是两级，别混**：
1. `movl_plan` 的 step_mm=1.0mm ⇒ 100mm 线算出 **101 个路径点**（只算不下发，
   用于体检：腕奇异 / 甩臂告警 / 弓高评估）
2. `sync` 的 stride 抽样（由 bow_mm 反推）⇒ 100mm 线只 **3 个航点**真正下发
⇒ **中间 98 个点根本没被走过**。2026-09-18 实测：定时注入的中间航点会被驱动器
   replan 丢弃，最终退化成一条长弦（实测 1.77mm ≈ 整段弓高 2.08mm）。
⇒ 增加第 1 级的密度对精度**毫无帮助**，只有第 2 级的段数才影响实际轨迹。

**⚠️ 修正：手册里没有"位置表/多段连续/前瞻"**
grep external/485通讯手册_sv126.1.md 的 位置表|多段|连续|轨迹|前瞻|队列 均无命中
（只匹配到 CRC 表）。此前记忆里"#3d 位置表是唯一两全出路"**未经手册核实**，

## 用户提议"实时 IK 解算路径"—— 前提纠正 + 真正卡点（2026-09-22）

**❌ 前提纠正 1：IK 不是瓶颈，也不是"只解一次"**
- 实测：10001 次 `ik`（含把 8 组解全打印）user+sys 共 0.40s ⇒ 单次 **<40µs**（含打印）。
  101 个点全解完 <5ms。而总线更新一次目标 ~90ms ⇒ IK 只占 4%。
- src **已经**解了 101 次：`movl_plan` 按 1mm 弦（100mm 线 = 101 点），每点一次完整 IK。
  只是这些点只用于体检，不直接下发。
- **second 才是"只解一次"**：grep 全项目 插补|interp|interpolat **零命中**；
  README 明写"整段一次 IK，不做笛卡尔插补"。⇒ second 不是更准，是更简单。

**真正卡点：总线节拍 vs 段行程时间（差 10~60 倍）**
- 总线：6 轴 × ~15ms/事务 = **90ms** 更新一次目标（等响应）；noread+4ms gap ≈26ms 但
  半双工 6 从站不安全（nrtest：3ms 起干净）
- 段行程：100mm@30rpm，1mm 弦只要 **1.4ms** ⇒ 轴走完干等 95ms
  这就 MOVL_STREAM_BEAT_S=0.10 那条注释的物理含义。
- 若把弦长放大到"段行程=节拍"（30mm/s ⇒ 3mm 弦 ⇒ 33 段）⇒ 弓高 0.008mm，理论上又直又不卡。

**🔴 关键未验证点（决定一切）：驱动器在"运动中收到新绝对目标"时速度会不会掉到 0？**
- 会 ⇒ 每节拍急停一次 ⇒ 更抖（2026-09-18 stream 实测确实更抖）
- 不会 ⇒ 连续，33 段 × 3mm 就是又直又顺
- 注意 sync 的卡顿是**等到位**造成的（判据=位置进容差 ⇒ 速度必然已归 0），不是插补造成的。
- 另：2026-09-18 那个"中间航点被丢弃退化成长弦"的现象，根因是**速度在开头按整段位移比
  一次性设死** ⇒ 各轴恒速比 ⇒ 关节空间直线。修法是每段重设速度（movl_set_seg_speed）。

**4 条路径**：
A 默认改 smooth（=second，零卡顿纯弧，改一个常量）
B stream + 不等到位 + 每节拍重设速度（若 replan 不减速则成立，零硬件改动）
C 速度模式(0x00C8连续运行+0x009A速度源) + PC 闭环 —— GRBL/Marlin planner 的对应物，
  但丢失驱动器位置环，10Hz 闭环精度差，安全责任全在 PC，风险高
D 6 路独立 USB-RS485 并行 ⇒ 更新一次 ~6ms ⇒ 节拍 10ms ⇒ 1mm 密集弦真正可行（硬件改动）

**github 参考**：要找的是 motion planner 不是 IK 库 —— grbl/grbl（look-ahead、
junction speed 段间不减速）、Marlin planner。**但它们在步进脉冲层面自己规划、
驱动器只当功率放大**；本项目的驱动器自己做梯形规划、PC 只给目标点 ⇒ 拿不到这个能力，
除非走 C（PC 自己做 planner + 发速度）。
