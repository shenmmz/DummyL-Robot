## 🔴 getpos 打印的"法兰倾角 0.00° / 垂直于地面"【不能当作证据】

**原因**：`commands.c:2252` 是先 `dh_forward(DH_TABLE, q, pose)` 再打印的，

**⇒ 它证明不了实际物理姿态垂直。编码器/零点一错，它就睁眼说瞎话。**
（与 #5 那条"别把 FK 吻合当物理验证"是同一个陷阱，这次栽在法兰姿态上。）

**⇒ 法兰是否真垂直，只能靠水平仪/角尺外部测量。**

### J5 零点（q4）标定方法

显示角 D 与物理角 P 的关系：`D - P = q0_true - q0_used`（常数偏差）。
设"程序判据满足时"的 J5 显示值 = D0（本例 71.06，即 `180 - (J2+J3)`）。

1. 法兰上贴水平仪（或手机水平仪 App）
2. 微调单轴 `movej:5:<角度>`，直到**实际**垂直
3. 记下此时 getpos 显示的 J5 = `D_r`
4. **`q4_new = q4_used + (D_r - D0)`**
   - 若 `D_r == D0` ⇒ 零点本来就对，别改
   - 差多少就补多少

## 10:05 【重要纠正】机械零点的正确标定方法 —— AI 之前的理解是错的

**用户原话**："机械臂每一个轴都是一个小凹槽，需要人手调整器对应好凹槽，这个
机械臂的机械原点。调好对应的凹槽之后对应的角度就是 0,0,90,0,0,0 这个姿态角度"

**AI 此前的错误**：说"回零后角度是 0,0,90,0,0,0 证明不了零点对"。

**错在哪 —— 混淆了两个完全不同的操作**：
| 操作 | 姿态由谁决定 | 读数性质 | 有无信息量 |
|---|---|---|---|
| 跑 `home` 命令 | 程序（堵转找限位→清零→退让） | 必然是 `ROBOT_HOME_MECH_DEG` 定义值 | **零信息**，与 q0 填什么无关 |
| **人手把六轴转到凹槽对齐** | **物理凹槽**（外部机械基准） | 对物理基准的**测量结果** | **有信息，是有效标定** |

用户说的是第二种。**凹槽对齐是机械原点的定义，q0 的正确来源就是
"对齐凹槽 → 读编码器 → 反算零点"，不是 FK 自洽、也不是 q2+q3+q5=180 判据。**

⇒ **q4 = 113.67 以用户的凹槽对齐为准，AI 推的 115.44 作废。**
⇒ 教训：判断零点对错，先问清楚**用户是用什么外部参照做的**，别急着套自己那套判据。
⇒ 凹槽对齐精度取决于加工+人眼（典型 ±0.5°~1°）；J5 差 1° ⇒ 笔尖偏 41.17×sin(1°)=0.72mm。
   要更高精度可在凹槽粗标基础上用水平仪精调，两者不矛盾。

## 10:30 落地：MoveL 支持"省略姿态 = 保持当前姿态"（根治姿态抄错）

**语法（三种，向后完全兼容）**：
| 写法 | 含义 |
|---|---|
| `MoveL:X,Y,Z` | **姿态保持当前不变**，速度默认 60/80/90 ← 推荐 |
| `MoveL:X,Y,Z,SPD,ACC,DEC,keep` | 姿态保持 + 自定义速度 |
| `MoveL:X,Y,Z,Rx,Ry,Rz[,SPD,ACC,DEC]` | 旧完整写法（姿态角须抄 getpos 原值） |

**歧义处理**：6 个数字段有两种解释，靠 `keep` 关键字区分。
带 keep ⇒ 后三个是速度参数；**不带 keep ⇒ 后三个仍是姿态角**（老命令不受影响）。
3 个数字段无歧义，直接判为姿态保持。9 段时若带 keep 会打印提示"keep 被忽略"。

**改动**：`cmd_parser.h` 加 `int keep_pose` 字段；`cmd_parser.c` MoveL 分支重写；
`commands.c` 的 `cmd_movel` 在 `keep_pose` 时用 `start_pose[3..5]` 覆盖 `end_pose[3..5]`

## 41.17 这个数的出处（用户追问，已查清）

是的。但**姿态不变时笔尖轨迹 = 法兰轨迹的整体平移**，形状尺寸完全不变

⇒ 因此 tool_length 是"读数直观性"问题，不是"画得对不对"问题，可择机再改。

## 真机 ↔ 3D 实时联动（UDP 回环单向镜像）

用户要"机械臂动、3D 跟着动"。**否决了实时写盘/管道**：控制循环一轮 92.8ms

**没人监听时内核直接丢包**（不连 Python 零副作用）。

**新增 `src/utils/telemetry.c/h`**：
- ini `[telemetry] enabled=1 / port=9900`（默认开）
- 所有失败路径【静默】：WSAStartup 失败/端口占用/网络异常都只设 g_disabled=1，
  不打印不报错不重试 ⇒ **遥测永远不能影响控制**，这是设计红线
- 包格式 `tag,t_ms,q1..q6`，tag = cmd（目标角）/ act（实际读回角）

**两个发送点**：
1. `movej_issue` 末尾：`if (num_joints == 6) telemetry_send(angles, "cmd")`
   —— 只在六轴齐全时发，否则未指定轴是残值，会摆出不存在的姿态
2. `movej_wait` 轮询循环内：`telemetry_send(g_tlm_mech, "act")`
   —— mech 是每轮读回的实际机械角，跟着轮询走（一轮约 90ms，轴陆续到位后更快）
   ⇒ **这包才是让 3D 连续动的关键**；只发 cmd 的话一段只有一包，3D 会一跳一跳

**⚠️ 第一版写错了，已修（实测坐实的坑）**：第一版条件是
`if (pend[1] && ... && pend[6])` —— 要求【六轴全部在动】才发 act。
结果只要有一轴已到位/被 mask，就一包都不发 ⇒ 真机跑整条 movej 只收到 **2 包且全是 cmd**。

### ★ 发现 1：Hg 的运动学跟本机真机**不是同一个几何**，差 52mm / 40°

**实测（t_hg_kin 第 1、6 节，判据用真机实测而不是模型自洽）**：
| 来源 | home(0,0,90,0,0,0) 末端 |
|---|---|
| 真机实测 | 241.50 / 52.00 / 286.00 |
| 标准DH（主程序 dh.c） | 241.500 / 52.000 / 286.000 ← 逐位吻合 |
| **Hg 连杆累加** | 241.500 / **0.000** / **338.000** ← Y−52、Z+52 |

反过来拿真机位姿喂 Hg IK，8 组解最接近的也差 **40.087°**
（期望 0,0,90,0,0,0；最优 19.12,−0.96,115.28,40.09,−30.57,−35.93）⇒ 下发会跑错地方。

**根因**：Hg 的 IK 三角形用 `l_ew=√(115²+52²)=126.2`、`atan_e=atan(52/115)=24.3°`，
前提是「肘部偏置 52 与大臂共面」。本机真机的 52 是**平面外**的（沿 z2，d3=52），
平面投影里只有 146 和 115。**FK 与 IK 是自洽的一对**。

**⚠️ 只改 FK 没用（实测坐实）**：`hg_kin_set_elbow_mode(1)` 把 FK 掰对后 home 算出
241.500/52.000/286.000 完全正确，但 **IK 结果一字不变、照样差 40.087°**
（因为 IK 用的是 l_ew/atan_e，跟 FK 的连杆向量无关）。要改必须 FK+IK 一起重推。

⇒ **结论：不能直接拿 Hg 的运动学控制本机。** 可借鉴的只有它的规划思想。

### ★ 发现 2：Hg 的 MoveL **根本没有笛卡尔插补**

`dummy_robot.cpp:737-835` 的 MoveL 只做三件事：跑一次 IK → 8 组解按软限位过滤 →
挑 `Σ|Δθ|`（AbsSumMaxOf6，名字叫 Max 其实是加权和，权重全 1）最小的那组 → `MyMoveJ`。
**没有插补循环、没有中间航点** ⇒ 末端走的是关节空间弧。

⇒ 这正好是主程序 `smooth` 模式的实测值（100mm 线弓高 8.70mm）**同一个东西**。
"直 vs 顺"的两条路线：Hg 选顺（驱动器一次规划到底，1 次启停），主程序选直（分段逼近）。
**主程序 #3d「驱动器位置表」是唯一能两全的路**，这条更该做了。

### 其他对齐结论
- **参数几乎全同**：L_BASE/D_BASE/L_ARM/L_FOREARM/D_ELBOW = 140/35/146/115/52 两边一致。
  只有 **L_WRIST(d6)：Hg=183，主程序=91.5** —— 这不是分歧，是口径：
  主程序把 d6 拆成「法兰偏距 91.5 + tool_length」，装夹爪填 91.5 就是 183。
  **Hg 的 183 = 装着夹爪的口径。**
- **姿态角分量顺序是反的**：Hg 的 (A,B,C) = Rz(A)Ry(B)Rx(C)，
  主程序 (Rx,Ry,Rz) = Hg 的 (C,B,A)。对接要交换，别照抄数字。
- **Hg 原文有个 ±π 缠绕 bug**：`if (q > M_PI) q -= M_PI`（该减 2π）。
  会把 200° 变成 20°。移植默认修正为 ±2π，`-DHG_WRAP_LIKE_ORIGINAL` 可复现原文。
- **Hg 的 MoveL 里那段 ±180° 相对当前角的归一化是对的**（:769-775），别跟上面那条混。
- 解选择：Hg 用 `Σ|Δθ|` 最小；腕部奇异时用 lastJoints 的 θ4/θ6 当锚
  （思路与主程序 ik_solve_ref 相同，但主程序阈值 1e-7 是由 double 分辨极限定出来的，
  Hg 用的是 cos 容差 1e-6）。

### 踩的坑（下次别再犯）
1. **随机数写错优先级**：`(seed >> 16 % 1000)` 在 C 里是 `seed >> (16 % 1000)`，

2. **单位**：对外传 mm 但内部当 m 用，FK 输出直接大 1000 倍。

2. 奇异分支把 `lastJoints->a[]`（度）直接当弧度 → 30° 输出 1719°
   （原文 6 处：qs[0]/qs[1]、qw[0][0]/qw[1][2]/qw[0][2]/qw[1][0] 及其 cos/sin）

收口成两个宏 `WRAP()` / `RAD_OF_LAST()`，开关从 KIN_WRAP_LIKE_ORIGINAL
改成 KIN_FIX_ORIGINAL_BUGS（语义反过来：默认是原文）。
CMake 加了 `t_kin_fixed` target 带该宏，两个 exe 并排跑做对照。

**复刻生效的实证**（同一代码只切开关）：
| | t_kin（忠实） | t_kin_fixed（修正） |
|---|---|---|
| 【3】最差还原误差 | **769.5055 mm** | **67.3253 mm** |
| 【6】真机反解差 | 40.087° | 40.087°（与这两 bug 无关） |
⇒ bug1 只影响 IK→FK 自洽性，与肘部偏置那 40° 是两个独立问题。

**核对方法（可复用）**：把两边代码 sed 归一化（去 float/double、去空格、
统一 atan2f→atan2、armConfig.→C_、变量名映射）后按"赋值/公式骨架"diff。
纯文本 diff 噪声太大（声明合并、(float) 强转、.a[] vs ->a[]），
**必须只抽含 `=`/atan2/acos/MatMultiply 的行**才比得动。

### A/B 对照台（"百分百复刻"的硬证据）—— second/tests/hgref/

读代码证不死复刻，只能喂同样输入比输出数字。做法：把 Hg 的 `6dof_kinematic.cpp`
**一行不改**编成 Windows exe（`#include "6dof_kinematic.cpp"`，不抄副本 ⇒ 原文改了这边跟着变），
与 `second/src/kin.c` 对拍。骗过 STM32 依赖只需 4 个空壳头文件（stubs/）：
stm32f405xx.h / arm_math.h（arm_cos_f32→::cos，注意原文 `inline cosf` 会递归）/ user_define.h / memory.h。

- `build_ref.sh` 编译原文；`ab.sh` 对拍：4 组 FK + 4 组位姿 × 8 解 = **68 项，全 PASS**
- 容差 FK 1e-3 mm / IK 1e-2 deg；**真正要看的是打印的"最大差"**，正常 1e-4~5e-3
- 奇异位形两边都输出 2111.831055↔2111.83、3257.746582↔3257.75，flag 同 [1 1 -1]
  ⇒ **连 bug 的输出都逐位一致**，这才是"百分百复刻"的凭据

**新发现（值得记住的物理风险）：±180° 分支切割**
原文 float / second double 在 ±180 处因 1e-7 噪声挑到相反代表值（−179.999985 vs 180.000）。
数学上是同一姿态，但**下发到电机差一整圈（关节 360° = 电机 50 圈）**。
⇒ ab.sh 里角度必须**取模比**（掩码 1=角度），并单独打"N 处 ±180 折返"提示。
⇒ 真机上若出现"到位了但轴绕了一圈"，先查这里。
