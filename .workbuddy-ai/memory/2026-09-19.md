## 用户拍板的两道新闸门（都已实现 + 验证 + 入库）

### 1. MoveL 规划层：单段关节跳变过大 ⇒ 直接拒绝（原来只告警）

阈值 ini `[safety] max_jump_deg` 默认 30°（编译期 `MOVL_JUMP_MAX_DEG`）。
判据抽成纯函数 `line_max_joint_jump()`（trajectory/line.c，可离线单测），
`movl_plan` 超阈值返回 **-4**（调用方要区分它和"逆解失败"，别套错文案）。

**⚠️ 我写错了一条后果描述，实测才纠正**：原以为"段时长只有几毫秒，关节
跑不完 ⇒ 猛冲"。**错**。时间表按关节限速自动把该段拉长到 **12.5 s**
（60 rpm、J4 减速比 50 ⇒ 7.2°/s）：这段时间里末端只挪 1mm，而 J4 转过
89.97°。真实后果是"臂以你完全没预料到的大幅度**慢慢**扫过去"。撞机概率
照样极高，但描述必须准确 —— 不准确的话下次会照着错误模型做判断。

**分离度实测**（test_ik_wrist 第 7 节）：病态 89.97° vs 正常 0.53~1.12°。

真机：`movel` +Y 30mm 被拒（"[拒绝] 规划路径第 1/11 段：关节4 单段要转 90.0°"），
**臂零动作**（getpos 未变）。

### 2. 越软限位 ⇒ 拒绝下发（原来单轴 MoveJ 完全不查）

`robot_angle_in_soft_limit()`（control/robot.c，纯函数）。返回 1/0/**-1**
（-1 = 关节号非法，与"越限"分开，两者处置不同）。
装在 CLI 层两处：`movej_issue()` + 单轴 MoveJ 分支。

**⚠️ 绝不能塞进 `robot_movej`**：回零（home.c）也走它，而回零的原理就是
朝一个方向顶到堵转 —— 起点已贴着限位、过程中必然越限。塞进去会让六轴
**全部回不了零**。这是这类"看起来该放在最底层"的检查最容易踩的坑。

真机：`movej:1:500` / `:1:-500` / `:4:400` 全拦；`movej:1:5`→`:1:0` 正常。
J4/J6 ±360° 整圈不受影响（已用单测锁住，防止日后被误伤）。

## 🚨 事故：MoveL 中途六轴读回变垃圾 + 急停下发失败（不可复现）

连续第 3 趟 ±Z 50mm 途中，六轴读回**同时**跳成越限值（J1=176.66 J2=-74.58
J3=180.03 J4=-4.27 J5=-115.44 J6=-84.89），偏差 258.92mm 冻结；随后六轴
「超时，已急停（**急停指令下发失败**）」；末了 getpos 报"部分关节读取失败"
给出全 0 假坐标。

**排除过程（每一步都要有证据，别猜）**：
1. **零点没丢** —— `zero` 读回与 ini `[joint_zero]` 逐位一致。那组"越限值"
   正好是 ini 零点的相反数，我一度差点据此断定"RAM 零点被改写"，是错的。
2. **没掉电** —— 事后六轴全在线、电流与历史保持基线一致 ⇒ 电机一直在保持，
   臂没掉。和 09-18 那次"J5 过流拉垮电源"（驱动器真重启）是两回事。
3. 全 0 的 getpos 只是**读失败的占位值**，不是真位置。

**恢复**：`movel` 回 home 一次成功（终点 285.99）。
**归因**：不是我当天改的代码 —— 故障前 6 趟、故障后原样复跑 4 趟
（0.22/0.21/0.21/0.21）全正常，且新闸门都在下发前生效、日志里一条没触发。
定性为瞬发总线/通信中断。

**软件侧暴露的缺口**：等到位循环靠读回判断，读回变垃圾就只能干等 60s 超时，
且急停还发不出去。建议加"连续 N 次读回越软限位 ⇒ 视为总线异常立即急停"，
但这需要真机复现才能验证，不要凭空写。

## 通用教训
1. **把判据抽成纯函数再写业务逻辑** —— 两道闸门都是先从 CLI 里抽出纯函数
   （`line_max_joint_jump` / `robot_angle_in_soft_limit`），才有单测覆盖。
   埋在 CLI 里的逻辑没法测，等于没有防线。
2. **后果描述要实测，不要脑补** —— "几毫秒跑不完"是我拍脑袋写的，实测是 12.5s。
3. **"该放在最底层"的检查，先问一句谁会因此废掉** —— 限位检查放进
   robot_movej 会让回零全废。
4. 测试通过 ≠ 功能正确：test_safety_gate 曾因路径依赖 CWD，从项目根绿、
   ctest 红。两种 CWD 都要跑。
